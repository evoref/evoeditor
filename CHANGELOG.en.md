# Changelog

[日本語](CHANGELOG.md) | English

This file records the changes of each version and is the source of the release notes (docs/12-licensing-distribution.md, docs/09-testing-quality.md §9).
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/).

Before v0.1.0, `0.0.x` was an internal counter of milestones; no tags or Releases were made for it (docs/11-dev-workflow.md §9.1).

The Japanese version ([CHANGELOG.md](CHANGELOG.md)) is authoritative. Both are updated in the same pull request.

## [Unreleased]

### Added

- **The beginning of a large or slow file is shown first**: when loading takes more than 0.2 seconds, the first part of the file (up to 1 MiB) is shown read-only while the rest loads. While loading you can scroll, move the cursor, select, copy, switch buffers, close, and cancel with `Esc`. The status bar shows, for example, "[First part 45%]". Search, replace, go to line, select all and extending the selection to the end of the document are not available until loading finishes, because their results would only cover the first part (they stay available while reloading or reopening with an encoding). When loading finishes, the whole file replaces the first part and the cursor, selection and scroll position are kept. While only the first part is shown, the document is not saved, edited, written to the swap file or included in the emergency save. Ordinary loading also changes as follows. Switching to a file that has finished loading now waits until input fields, confirmations, the command palette, the buffer list, help and the search bar are closed (so does returning to the previous document after a failed or cancelled load). `Esc` now cancels only the loading of the shown document (when the shown document is not loading, it still cancels files being opened, as before). An `Esc` that dismisses a warning no longer also cancels loading. Trying to edit a document that is loading now says "Cannot edit while the file is loading" and suggests waiting or cancelling with `Esc` (the reason used to be empty). Save As and Save on a loading document now say that it is loading, instead of asking for a name or silently doing nothing. The buffer list marks loading documents with "Loading".
- **Shift_JIS / EUC-JP / ISO-2022-JP files keep the original bytes of the parts you did not edit**: characters that have more than one byte representation (such as the duplicated NEC special characters and IBM extensions of CP932), EUC-JP supplementary kanji (JIS X 0212), and ISO-2022-JP lines with a different choice of escape sequences (such as old JIS `ESC $ @`) or with half-width katakana are remembered with the bytes they had when the file was opened, and the parts you did not edit are written back as they were. Parts that you edited and then restored with Undo are also written with the original bytes. Previously, saving after an edit changed all such places in the file to the standard bytes (the characters did not change). Before writing, the editor checks the remembered bytes, reads the output back and checks that it matches the text; if it does not, nothing is written (a safeguard against bugs; it should not happen). In that case the original bytes of that file are no longer kept, and saving again writes the file without them after a confirmation.
- **Files with supplementary kanji or half-width katakana can be saved after editing other parts**: previously, saving an EUC-JP file with supplementary kanji (JIS X 0212) or an ISO-2022-JP file with half-width katakana stopped with "characters that cannot be represented", even when you edited other parts, and you had to choose to replace them or save as UTF-8. Unedited supplementary kanji and half-width katakana are now saved with their original bytes. "Replace and save" also leaves the characters in unedited parts alone (supplementary kanji and the like that you typed are still treated as characters that cannot be represented).
- **Files with invalid bytes can be edited after a confirmation**: files with invalid bytes (shown like `<0x9A>`) still open read-only. Running "Toggle read-only" (`file.toggle_read_only` in the palette) shows a confirmation with the encoding, the number of invalid bytes, the first position, and what to keep in mind (saving writes them back as the original bytes, deleting one removes that byte from the file, one joined with the text next to it reads as a different character when reopened, and pasting into other applications gives the text `<0xNN>`); choose "Allow editing" to edit. When you edit other parts and save in the same encoding, the invalid bytes stay as the original byte values in the same order. If the text looks garbled, choose "Reopen with encoding" in the confirmation instead. Files opened read-only from the "many invalid bytes" confirmation can also be made editable. Reloading the same file keeps it editable (undo can bring back the content before the reload); reopening with an encoding or opening it again makes it read-only again. ISO-2022-JP files with invalid bytes, binary files, files opened as huge files, and files with both invalid bytes and private-use characters still cannot be edited. The message shown when you type in a read-only document now tells, for each reason, how to make it editable (or that it cannot be).
- **Saving where an invalid byte would join the text next to it asks before writing**: in a file you allowed editing, putting invalid bytes next to each other or text right after an invalid byte can make the saved file read as different characters when reopened (for example, UTF-8 `<0xE3><0x81><0x82>` becomes "あ"). When saving, before writing anything, the editor shows how many places are affected, the first position, how much text changes, and a list of what each place becomes, and asks. The default is Cancel, which highlights those places; "Save as is" saves it unchanged.
- **A file with invalid bytes can be recovered after a crash while editing**: the swap of a file you allowed editing is offered for recovery the next time you open it, even though it opens read-only again. After applying it, the document stays read-only; allow editing with "Toggle read-only" to continue. If the file was opened with a different encoding from the one the swap was written with, the recovery is not offered; the editor tells you to reopen with that encoding, and offers it after you do.

### Changed

- **The confirmation before saving ("saved with different bytes" and the like) appears only for files whose original bytes could not be kept**: it no longer appears for files whose original bytes are kept. For files whose original bytes were not kept (a very long line stopped the check, there were too many such places, the document was recovered from an emergency save or a swap file, and so on) and files where some places could not be kept (an ISO-2022-JP line that ends in the Roman or another non-ASCII state, and so on), you are asked even without edits when you save under another name or with Set Encoding in the same encoding. The notice shown on opening ("some characters in the edited places may be saved as different bytes") also appears only for such files, with wording that fits them.
- **Faster regular-expression search, and faster case-insensitive search for some words**: on large files with many lines, the per-line setup cost is reduced. On a 100 MB file, a full scan with a regular expression that matches rarely went from about 1.5 s to about 0.1 s (measured on a development machine). Regular expressions that start with a character class, such as `\d+`, went from about 4.5 s to about 0.2 s, helped by a change to how the regular-expression engine is configured. Search results are unchanged.
- **The cursor now stops before a combining character that follows an invalid-byte mark**: when an invalid byte (shown as a mark such as `<0x9A>`) was followed by a combining character (such as an accent), a variation selector or a ZWJ, moving left or right skipped both at once and the cursor could not be placed between them (even though they were shown as separate marks). The cursor now always stops before and after an invalid-byte mark, matching what is shown. Word movement treats a run of invalid-byte marks as one word.
- **Large files open faster**: the editor no longer re-reads the whole text after loading to count line endings and long lines; it counts them while loading. On a 100 MB file, the time to finish opening dropped by about 30% (measured on a development machine).
- **Shift_JIS / EUC-JP / ISO-2022-JP files open and save faster**: the check on opening for places that would be saved with different bytes, and the check before saving, no longer create a working string and a decoder for each line or section. On a 10 MB ISO-2022-JP file, the time to finish opening dropped by about 40%, and saving a 100 MB Shift_JIS file got about 10% faster (measured on a development machine). Files with many places whose original bytes are kept (such as a file with such a character on every line) now open and save with almost no extra time. The saved content is unchanged.
- **A clearer explanation when you try to save a file with invalid bytes in another encoding**: invalid bytes (shown as marks such as `<0x9A>`) can be written only in the original encoding. Previously the message said "N characters cannot be represented in UTF-8" and the like. It now shows the number of invalid bytes and the first position, and tells you to delete them or retype the correct characters before saving. If other characters cannot be represented either, their number is added.
- **Copying invalid bytes gives other applications text such as `<0x9A>`**: when you copied a range containing invalid bytes (shown as marks such as `<0x9A>`), the system clipboard used to receive private-use characters (U+10FF00 to U+10FFFF). It now receives the same `<0x9A>` text as shown on screen. Only when you paste inside the editor into a document with invalid bytes of the same encoding are they inserted as bytes, with the message "Pasted N invalid bytes as bytes". Other documents receive the `<0x9A>` text, and the editor tells you so.
- **Private-use characters U+10FF00 to U+10FFFF from outside are inserted as text such as `<U+10FF80>`, with a message**: these characters are the same characters as the invalid-byte marks. Previously, such characters inserted by pasting, typing or replacing stopped the save as characters that cannot be represented. They are now inserted as text such as `<U+10FF80>`, and the editor tells you so (in a file that already contains characters in this range, they are inserted as they are).
- **Regular expressions can search with `[^\n]`; a line break written as a code point such as `\x0A` is shown as unsupported**: a regular-expression query is now rewritten according to the rules for line terminators (line breaks) before searching, as preparation for searching across lines. `[^\n]`, which was "patterns with line breaks are not supported", now searches within a line (`[^\n]` does not match a lone CR line break either). A query that writes a line break as a code point, such as `\x0A` or `\x{D}`, used to find nothing without a message; it is now shown as unsupported, like `\n`. Preparing (compiling) a regular expression has also moved from input handling to the search work, so for regular expressions and for some case-insensitive searches (words with `k`, `s` or other non-ASCII cased letters, and case-insensitive whole-word searches) the highlights and the current match appear when the first search results arrive (a few milliseconds later). Pressing `Enter` in the replace field before then does not replace anything (press `Enter` again once the match is highlighted). "Invalid regular expression" for an expression that is too large also appears then (even after `Enter` has moved to the next match). Regular expressions with a very large repetition are now reported as too large at a slightly lower size.
- eve-view: added `Partial` to `LoadStateView` (while the head of the file is shown before loading finishes; like `Loading`, `DocumentText` / `Selection` answer `NotLoaded`) (addition only; `#[non_exhaustive]`; docs/02 §8.4 C2, docs/03 §9.2.1).

### Fixed

- **A file with a BOM could not be saved in place after deleting all of its text**: when you deleted all the text of a file with a BOM (UTF-8 or UTF-16) and the save used direct overwrite (for example, for a file in a location where replacement is not possible), the save failed and the file kept its old content. The size estimate made before writing did not count the BOM.
- **No confirmation before saving some Shift_JIS / EUC-JP / ISO-2022-JP files with a very long line**: when a line was longer than 4 MiB, the places after it that "will be saved as different bytes for the same characters" were not checked. If such places existed only after that line, saving after an edit changed their bytes without asking (the characters did not change). A file that could not be fully checked now asks for confirmation when you save it in its original encoding after an edit (Issue #495).
- **With more than 100 characters that cannot be encoded, an invalid-byte marker could become `?` with "Replace and save"**: when the characters that cannot be encoded in the target encoding include an invalid-byte marker (a character shown like `<0x9A>`, for example one pasted from a file with invalid bytes), only Cancel should be offered, not "Save as UTF-8" or "Replace and save". The check looked only at the first 100 such characters, so when a marker appeared only after the 100th, "Replace and save" was offered and, if chosen, saved the marker as `?` (the original byte was silently lost). The check now covers all of them, and "Replace and save" never replaces a marker.
- **Invalid bytes in ISO-2022-JP files were not shown like `<0x0A>`**: when a file opened as ISO-2022-JP had invalid bytes (for example, a line break in a line that stays in the kanji state), they were not drawn as a symbol such as `<0x0A>` but as an undisplayable character (a box, a blank, and so on). They are now shown as symbols, as in other encodings, and cursor movement uses the symbol's width. The same applies to an invalid-byte marker pasted into an ISO-2022-JP file without invalid bytes. Saving is unchanged (such a file is still not saved as ISO-2022-JP).
- **"Save as UTF-8" was offered when saving invalid bytes back as their original bytes**: when a file with invalid bytes was saved in the same encoding (for example, with Save As) and it also had characters that cannot be represented, the confirmation offered "Save as UTF-8". Choosing it led to another "characters that cannot be represented" confirmation with only Cancel, because the invalid-byte markers cannot be represented in UTF-8. "Save as UTF-8" is no longer offered for such a save (the other choices are unchanged).
- **Saving a file with both invalid bytes and private-use characters under another name wrote the invalid bytes as private-use characters**: when a file that has both invalid bytes and private-use characters (U+10FF00 to U+10FFFF; such a file opens read-only) was saved under another name in the same encoding, the invalid bytes were written not as the original bytes but as private-use characters (4 bytes each in UTF-8). Because invalid bytes and private-use characters cannot be told apart in such a file, saving it in any encoding now stops with "characters that cannot be represented" without writing anything, and only Cancel is offered (reopen it with a specified encoding to work with it). Also, whether an invalid-byte marker (a character shown like `<0x9A>`) is written back as its original byte is now decided by which encoding the document remembers the markers to be bytes of. Markers are written as their original bytes only when saving in that encoding; markers brought back by Undo after saving in another encoding, and markers recovered from a swap file written in another encoding, are not (so that bytes of one encoding are never written into a file in another).
- **A file with many invalid bytes opened read-only stayed read-only after reopening it with the correct encoding**: choosing "Open read-only" in the "many invalid bytes" confirmation on opening also added the "requested by the user" reason (the reason used for `--readonly`). Because of it, the document stayed read-only even after you reopened it with the correct encoding and the invalid bytes were gone. Choosing "Open read-only" in a confirmation now adds only that confirmation's reason (invalid bytes, binary, or huge file), and reopening with the correct encoding makes the document editable. The reason shown for the read-only state is now "file with invalid bytes" instead of "opened read-only by request (`--readonly`)". A file opened with `--readonly` stays read-only after reopening, as before.
- **Saving a document with invalid bytes as ISO-2022-JP asked for a file name before saying it cannot be saved**: a document with invalid bytes cannot be saved as ISO-2022-JP (nothing is written). However, for a read-only or untitled document, Set Encoding with ISO-2022-JP, Save As without a target, and choosing "Save" in the confirmation on quitting or closing first asked for a file name, and only after you entered one said that the document cannot be saved as ISO-2022-JP. The message now appears before any name is asked for (and quitting or closing does not proceed). Save All lists such a document among the documents that could not be saved, with this reason.
- **Replacing with an invalid search pattern said "Enter the text to search for"**: running Replace All or Replace with a regular expression that has a syntax error, or with a pattern that contains a newline (not supported), showed the message for an empty search. The message line now shows the same error as the search bar ("Invalid regular expression" with the reason, or "Patterns that contain a newline are not supported"), and that nothing was replaced. The document is not changed (as before).
- **Case-insensitive search did not match `ſ` (U+017F LONG S) for `s`**: in a case-insensitive search (the `Aa` toggle off, or smart case with a lowercase-only pattern), `k` matched `K` (U+212A KELVIN SIGN), but `s` / `S` did not match `ſ` (regular-expression search did). Literal search now matches with Unicode case folding, the same as regular expressions (also for whole-word search and replace). Letters-only patterns that contain `s` are now searched on a slightly slower path (a full scan of a 100 MB file went from about 0.03 s to about 0.05 s, measured on a development machine). Letters-only patterns that contain `k` moved to the same path and got faster (from about 0.6 s to about 0.25 s on the same file).
- **Save As could save a different document when another file finished loading while you typed the name**: if you opened Save As on the current document while another file was still loading, the display could switch to the newly loaded file before you confirmed, and the switched-to document was saved instead. Choosing Overwrite in the following confirmation overwrote the original file with the other document's contents, and the original document stayed unsaved. The Save As, Set Encoding and Reopen with Encoding inputs, and the file-name input opened from save confirmations (such as after a failed save), now act on the document they were opened for. If that document has been closed in the meantime, nothing is done and a message says so.

## [0.3.0] - 2026-11-08

The first release of v0.3. It reorganizes and speeds up the internals without changing behavior, and fixes data-safety and correctness bugs. It also adds the remaining v0.2 commands (Save and Quit, Quit with Error, Show Settings Diagnostics) and word editing and select-all in input fields.

### Added

- **Save and Quit (`app.save_and_quit`)**: saves the current document, then quits, in one step (for example, when you finish writing a `git commit` message). An untitled document asks for a name, and nothing quits if the save fails. If other documents have unsaved changes, you are asked as when quitting. Run it from the command palette (it has no default key).
- **Quit with Error (`app.quit_with_error`)**: quits without saving, with exit code 4 (like Vim's `:cq`). Use it to abort `git commit` and the like from the editor. If documents have unsaved changes, you are asked as when quitting. Run it from the command palette.
- **Show Settings Diagnostics (`config.show_diagnostics`)**: lists the problems in the settings file, the keymap and the theme (including items this version does not support), and Enter opens the file at that line. The message at startup or after reloading the settings showed only the first problem; now you can see all of them on screen. When there are none, it says so. Run it from the command palette.
- **The status bar shows files changed outside evoeditor**: a document for which you chose "Ignore" when an external change was found (for example, when you came back from another app) shows `[Changed on disk]` (`Changed` when narrow) in the status bar. It disappears when you save, reload or reopen the document. You can now tell that the content on screen differs from the file on disk after the dialog has closed.
- For developers: the generated reference in `docs/reference/` (commands, the default keymap and the default settings) and `cargo xtask gen-reference`, which writes it (`--check` checks that it is up to date and matches the command catalog in the spec; it is part of `cargo xtask check`). Added the hidden options it reads, `--list-commands [--json]` and `--dump-keymap [--json]` (the keymap with your `keymap.toml` applied). They are not shown in `--help` (docs/09 §11.2). `--check` also checks that the commands of catalog rows annotated with an already shipped version are registered.

### Changed

- **The command palette lists the shorter name first among equally good matches**: for example, typing "save" puts Save above Save and Quit (so that Enter does not quit).
- **`Ctrl+Shift+K` now deletes the line** (as in the spec's key table). It reaches the editor only on terminals with enhanced keys; elsewhere use `Ctrl+K L` as before, which the palette and help show instead.

- **"What it does" and "Known limitations" in the bundled `README.md` / `README.en.md` now match the features of v0.2**: the heading "Known limitations (v0.1)" is now "Known limitations". Limitations removed in v0.2 (only one document, no regular expressions, no help screen, no OSC 52, long lines opened read-only, external changes not reported until you save, Japanese-only UI, no Linux support, and so on) were dropped, and the current ones were added (edits after the last swap write are lost on forced termination, external changes are checked only for the document on screen, some keys do not arrive on terminals without enhanced keys, and so on). The "Starting" examples now include several files and `+line`.
- **Five bindings that terminals cannot tell apart without enhanced keys are now treated as needing enhanced keys, as the spec says**: `Ctrl+Shift+S` (Save As), `Ctrl+Shift+Z` (Redo), `Shift+F3` (Find previous) and `Ctrl+Shift+Home` / `Ctrl+Shift+End` (select to the start / end of the document). On terminals without enhanced keys, the help key list marks them as not reachable, and key hints in the palette, messages and elsewhere show a reachable alternative instead (`Ctrl+K S` for Save As).

- eve-view: changed the type of `DocumentInfo.read_only` from `Vec<String>` (variant names as strings) to `Vec<ReadOnlyReasonView>` (a new enum) (breaking; the `Query::Documents` answer). Aligned the documentation of `Capabilities.osc52_write` and `InputEvent::Resize` with the implementation (no type change).
- eve-view: added `ExternalChange` (a document whose external change was ignored) to `StatusKind` (addition only; docs/04 §8.7).
- eve-view: added `key_notation(strokes, ascii)`, the function that formats keys for display (addition only; shared by the core and eve-tui, docs/04 §7.8).

### Fixed

- **The modified mark in the terminal title did not follow the spec**: the title started with `* `, as in `* a.txt - evoeditor`. It is now `a.txt ● - evoeditor`, as docs/04 §3 says. With two or more documents, the mark comes after the position (`a.txt (2/3) ● - evoeditor`).
- For developers: the description of a syntax error in a condition expression (`when`, the `Display` of `ParseError`) counted the position from 0 ("character 0"). It now counts from 1 (the value of `ParseError.pos` is still 0-based).
- **Every untitled document was named "Untitled-1"**: with two or more untitled documents open, the buffer list, the status bar, the terminal title, swap files and the emergency rescue record could not tell them apart. Untitled documents are now numbered in order for each run (`Untitled-1`, `Untitled-2`, ...), and a number is not reused after its document is closed.
- **Word movement, word deletion and select all did not work in input fields (the prompts such as Open and Save As, the command palette, the buffer list and the search bar)**: `Ctrl+Left` / `Ctrl+Right` (move by word), `Ctrl+Backspace` / `Ctrl+Delete` (delete a word) and `Ctrl+A` (select all in the field), which are in the key table of the spec, were not bound. After select all, typing or pasting replaces the whole field, `Backspace` and similar keys clear it, and `Left` / `Right` cancel the selection.
- **Bindings written in `[keys.palette]` of the keymap also took effect in the buffer list**: list navigation (`Up` / `Down`, `Ctrl+N` / `Ctrl+P`, `PgUp` / `PgDn`) is now in `list`, the context shared by list UIs, as the spec says, and the buffer list no longer reads the palette bindings (`palette`). To change list navigation, write it in `[keys.list]` (it applies to both the palette and the buffer list).
- **The Message History key `Ctrl+K M` also worked while an input field, the help, the search bar or another overlay was open**: it is now an editing-area binding (`editor`), as the spec says. It does not work inside overlays or the search bar; close them first (you can still open it from the command palette).
- **"Abort saving and quit" could cut off the rescue of a large document**: the rescue had a 3.5-second limit, so a large document or a busy system could make it quit before the rescue finished. Because you chose to quit, it now finishes writing before quitting.
- **The emergency rescue (for example when the console window is closed) could end before writing the text under heavy load (part of issue #342)**: the rescue time budget now counts from when the signal is received, and is also checked before writing each document and before updating the record. If the rescue record (manifest) cannot be written, the rescue is no longer reported as complete. Each rescue stage is now logged (`log/evoeditor.log`) to help find the cause.
- **The emergency rescue could run out of time while waiting for the disk, leaving the text unrecorded (issue #342)**: the rescue now first writes the text of all documents without waiting for the disk (the text survives even if the process is killed), and confirms the writes on disk with the remaining time. The rescue record (manifest) now tells documents that were written (`stored`, with the text's XXH3-64 in `xxh3`) from those confirmed on disk (`written`). The exit message shows how many saved documents could not be confirmed on disk.
- **Config diagnostics showed numbers in a different form than written**: a number written in hexadecimal, octal or binary, or with `_` separators (for example `tab_width = 0x11`), was shown without its prefix and separators (`11`) in out-of-range and other diagnostics, so it looked like a different value. It is now shown as written.
- **Some config diagnostics had broken wording or no position**: for items without a default (a section written as a value, a wrong theme color), the hint said "This item uses the default " with an empty default (it now says "This item is ignored"). Diagnostics for unbinding the escape key (`"ctrl+q" = "none"`) and for an unknown role in a theme file now show the line and column where they were written.
- **Some non-setting names in the config file were silently ignored instead of warned about**: writing a name that is not a setting key (a command or a color role name), such as `[ui] palette_open = 1`, gave no warning. The list of reserved keys now matches the spec table, and such names are reported.
- **Moving a multi-line selection up or down broke the selection from the second move**: with lines of different lengths, the selected range shifted from the second move on. The same lines now stay selected however many times you move them.
- **Undoing a line-ending conversion also reverted a later encoding or BOM change**: undo now restores only the line ending (a later save uses the encoding you chose).
- **Reloading a file could move the cursor to a different line**: after the file was changed externally near the top, reload kept the same byte offset and the cursor jumped to another line. It now stays at the same line and column (in characters).
- **The line-ending and long-line counts could go wrong after replacing in many places at once**: after edits that change several places in one step, or that join or split CR and LF, the status bar's line-ending indicator and the long-line count could disagree with the text.
- **Keys were written differently depending on where they appeared**: the help key list, keys inside messages and the display after `Ctrl+K` showed `Ctrl+PageDown` and `Ctrl+Shift+Up`, while the command palette and the hint bar showed `Ctrl+PgDn` and `Del` for the same keys. All places now use `PgUp` / `PgDn`, arrow symbols such as `↑` (`Up` etc. when box drawing is limited to ASCII), and `Delete` / `Insert` / `PrintScreen`.
- **The "characters that cannot be saved" confirmation for Shift_JIS / EUC-JP could point to a later character first**: when a character that changes into another character on saving (such as `¥`) came before a character that cannot be represented, the confirmation showed (and moved to) the later one first. Characters are now reported in document order.
- **`--check-config` printed message keys for settings not supported in this version**: with a reserved section such as `[ai]`, or `preset` directly under `[keys]` in the keymap, `evoeditor --check-config` printed the message key as is (such as `msg.config.unsupported.text`). It now prints "{item} is not supported in this version and was ignored".
- **Reopening with another encoding could lose another document's unsaved changes**: after choosing "Reopen with Encoding" on a document with unsaved changes and choosing "Save" in the confirmation, switching to another document with unsaved changes before the save finished made evoeditor reopen the document you switched to, without asking, discarding its unsaved edits and undo history. Only the saved document is reopened now.
- **Saving a file with invalid bytes in another encoding produced a broken file**: when a file containing invalid bytes was saved in another encoding (such as UTF-16) with "Save with Encoding", evoeditor wrote the original invalid bytes as they were, producing a file in which the following characters were shifted (or merged with the neighboring bytes), and reported that the file was saved. Invalid bytes are now treated as characters that cannot be represented when saving in another encoding: nothing is written and a confirmation is shown. Invalid-byte markers pasted from another file are handled the same way.
- **The automatic backup of unsaved changes (swap) was removed too early, for example after a failed save**: the swap of a document whose save failed for lack of write permission, or of a document switched to read-only with unsaved changes, was removed before the changes were saved, so a forced termination or power loss afterwards lost the edits. The swap is now removed only when the unsaved changes are gone (saved or discarded) and at a normal exit. A swap under the old path also no longer remains after "Save As" changes the path (it could offer to recover stale content at the next start).
- **"Abort Save and Quit" could exit without telling where the original file was moved**: choosing "Abort Save and Quit" while a save was running treated a save that failed after replacing had started (the original file moved to a backup name, or a direct overwrite that failed midway) as cancelled, and exited without showing where the original file was. Such failures are now reported with the backup location at exit even after the cancellation is sent. The failure list of "Save All" also shows the backup location of the original file.
- **Warnings about a successful save were not shown**: evoeditor only showed "Saved" even when the write to the disk could not be confirmed on a network or removable drive (fsync failure), when another program may have changed the file right after the save, when some permissions or attributes could not be carried over, or when the temporary name of the moved original file could not be deleted. The most serious one is now shown as a warning after the save completes.
- **An unexpected error in input handling could leave the terminal unusable**: when the thread that reads input stopped abnormally, the editor did not notice, so the terminal stayed in its special mode without accepting input, and unsaved changes were not backed up. The editor now notices it, backs up unsaved changes, restores the terminal, and exits. It also guards against very large numbers in control sequences from the terminal (such as crafted input).
- **On Linux, saving a file of another group could make it readable by a different group**: when saving a file whose group you do not belong to, evoeditor applied the original permissions (and a shared ACL) to your own group. When the group cannot be kept, the file now gets owner-only permissions with a warning that the permissions for other users became narrower. Also fixed: when the cleanup after a failed save could not delete the temporary file, the mark used to find it at the next start was deleted too; and on some file systems (network, FUSE and others) where an atomic replace is not possible, evoeditor did not proceed to the confirmation for a direct overwrite.
- **Saving read-only documents, and handling around reopening**: fixed the following. Choosing "Save" in a confirmation (such as at exit) for a read-only document with unsaved changes (for example, one switched to read-only) wrote to the same file (it now asks for a name). A save could start while a document was being loaded (during a reopen or reload). The result of an operation started before reopening (such as Replace All) could be applied to the reopened document. After a successful direct overwrite, a failure of only the final status check was reported as "could not be saved" (the save now stays successful with a warning that it could not be confirmed).
- **Crash logs were created readable by other users and kept growing**: the crash log written to the state folder after an abnormal exit is now created readable only by you, like the other files there, and only the latest 20 are kept.
- **Opening or reloading a huge file with too little memory crashed the editor**: when the memory needed for loading could not be allocated, evoeditor terminated without backing up the unsaved changes of other documents. It now checks whether the memory can be allocated before reading and, if not, shows "Loading ... was stopped because memory ran out" and keeps running (a reload keeps the previous content).
- **Reloading a large file kept several times its size in memory**: reload copied the new content and the previous content kept for undo, so memory grew by about six times the file size. The copies are gone and memory now grows only by the new content. Deleting everything after selecting all also no longer copies the content kept for undo.

## [0.2.0] - 2026-11-04

The first release of v0.2. The only product changes from [0.2.0-rc.1] are dependency updates (`signal-hook` 0.4, `unicode-width` 0.2.3, `encoding_rs` 0.8.44) and an adjustment that keeps the width of the half-width katakana voiced and semi-voiced marks (`ﾞ` / `ﾟ`) at 1 regardless of the `unicode-width` version; there is no user-visible difference. This release fills everyday gaps and **adds Linux (x86_64 / aarch64)**. It adds automatic saving of unsaved content and recovery, multiple documents, regular-expression search and replace, soft wrap, mouse, themes, an English user interface and more. Downloads are the Windows zip and the Linux tar.gz on GitHub Releases; installation, updating and known limitations are in the bundled `README.md` (English: `README.en.md`). When updating from v0.1.0, settings and rescued files keep working as they are.

### Added

- **Linux support**: a statically linked executable (musl, x86_64 and aarch64) that runs on any distribution, distributed as a `tar.gz`. Settings and state use the XDG locations (`~/.config/evoeditor/`, `~/.local/state/evoeditor/`). When the terminal is closed or on `kill` (SIGTERM / SIGHUP / SIGINT), evoeditor rescues unsaved content before quitting, and `Ctrl+K Z` returns to the shell temporarily (come back with `fg`). The clipboard uses `wl-copy` / `xclip` / `xsel`, `powershell.exe` on WSL, and OSC 52 when none of them is available or over SSH. The environments checked are Windows Terminal on WSL2 and tmux.
- **Automatic saving of unsaved content (swap) and recovery**: edited content is written to the state folder about 2 seconds after the last input. After a forced termination or power loss, opening the same file (or starting untitled) asks "Apply recovered content / Discard swap". Applying does not change the file until you save, and can be undone. Documents larger than 64 MiB, read-only documents, and files that may contain secrets (`.env`, `*.pem`, `id_rsa*`, and so on) are excluded. Settings are in `[file.swap]`. Temporary files and backups left by an interrupted save are also found on the next start, with a proposal to restore or clean them up.
- **Multiple documents**: open several files and switch between them (`Ctrl+PageDown` / `Ctrl+PageUp`, list with `Ctrl+E`, close with `Ctrl+W`, save all with `Ctrl+K A`). The command line accepts several paths, `+line` and `path:line:column`. On quit, unsaved documents are confirmed one by one. The undo history is kept under a total limit across all documents (default 256 MiB, `[editor.undo] total_max_bytes`) by discarding the oldest entries.
- **Search and replace**: regular expressions (`Alt+R`), whole words (`Alt+W`) and search within the selection (`Alt+L`), replacing one match at a time (`Enter` in the replace field), and regular-expression replacement (`$1` / `${name}`).
- **Display**: soft wrap (`Alt+Z` / `Ctrl+K O`), showing whitespace (`view.show_whitespace`), built-in themes that paint the background and theme files, switching themes, and an explicit color depth (`truecolor` / `256` / `16` / `none` for `[theme] color_mode`). Lines longer than 1 MiB can now be edited.
- **Editing and input**: duplicate, delete and move lines (`Ctrl+K D` / `Ctrl+K L` / `Alt+Up` / `Alt+Down`), mouse (click, drag to select, wheel), overriding key bindings (`keymap.toml`), the unit that Backspace deletes, a guide to the keys available after `Ctrl+K`, enhanced keyboard protocols (kitty and xterm modifyOtherKeys, on terminals that send keys with `Ctrl+Shift` distinctly), and the clipboard through OSC 52.
- **Help and messages**: a help screen (`Ctrl+K H`, keys and commands), the message history (`Ctrl+K M`), and fuzzy search in the command palette. The first start of a new version shows the highlights of that version in one line (no network access).
- **English user interface**: the user interface can be shown in English. The language is chosen in the order `--locale ja|en` > setting `[ui] locale` > environment variable `EVE_LANG` > the OS display language; if none applies, Japanese. The stderr lines of `--help`, usage errors, panics and exit show the English (ASCII) line first and the Japanese line indented by two spaces next. English versions of the user README and the changelog are bundled.
- **Settings and command line**: reloading settings (`config.reload`), `--set key=value`, `--check-config`, `--dump-config` and `--crash-report`. The thresholds for huge files and long lines (`file.huge_file_warn_bytes`, `file.long_line_threshold`) can be set.
- **Protecting files**: external changes are checked when you come back from another application (focus regained) and with `file.check_external_changes`. Toggling read-only (`file.toggle_read_only`) and "remove read-only and save", creating the target when saving through a symbolic link whose target is missing, keeping extended attributes, ACLs and alternate data streams on Windows, and rescuing on Windows log-off and shutdown.

### Known limitations

See "Known limitations" in the bundled `README.md`. Main ones: macOS is not supported (it cannot be checked on real hardware yet; a later version). On Linux, the clipboard and the Japanese input candidate position on desktop environments (GNOME / KDE) have not been checked. In Windows Terminal on WSL, `Ctrl+Shift+<letter>` is not told apart from `Ctrl+<letter>` (use `Ctrl+Y` to redo). The executable is not signed (SmartScreen, Smart App Control).

### Fixed

- **Secret-file marker of emergency rescues**: when a document whose file name may contain secrets (`.env`, `*.pem`, `id_rsa*`, `.ssh/**`, and so on, docs/07 §5.12.2) was rescued, `sensitive = true` in the manifest and the "please delete it" note on exit were missing. They are now shown. The rescue itself already happened in v0.1.0, and no data was lost.
- **Emergency rescue gave up the rest after one failed write**: with several documents to rescue, a failed write of one (permissions, locking) ended the rescue without the documents after it. Now only the failed document is marked `written = false`, and the rescue continues for the rest (only a timeout stops it). This prepares for multiple documents in v0.2; it could not happen in v0.1.0 with a single document.
- **Keep the content of a closed document that is being saved in the emergency rescue**: closing a document while its save was running removed its content from the rescue targets. It is now kept until the result of the save arrives, and written to the rescue location if the save fails.

## [0.1.0] - 2026-10-27

The first release of v0.1 (the minimal core). The product code is unchanged from [0.1.0-rc.1] (only the specification and records changed after rc.1). It is a text editor with a Japanese user interface that runs in Windows Terminal and the console host on Windows 11 (x86_64). The only distribution is the zip on GitHub Releases; installation, updating and known limitations are in the bundled `README.md`.

### Added

- **Reading and writing files**: detects and opens UTF-8 (with or without BOM), UTF-16 (LE/BE), Shift_JIS, EUC-JP and ISO-2022-JP, and saves **in the original encoding, BOM, line endings (LF/CRLF/CR, including mixed) and presence of a final newline**. Also supports reopening with a given encoding, saving with a different encoding and line ending, and reloading (undoable).
- **Safe saving**: atomic saving through a temporary file and replacement, so the original file is not damaged if it stops halfway. Permissions, attributes and alternate data streams are kept, and symbolic links and junctions update their targets. Failures such as hard links, read-only, no write permission, sharing violations and a full disk show the reason and what to do next. "Save to the rescue location" is available when saving is impossible.
- **Detecting external changes**: just before saving, the file's modification time, length and ID are checked, plus a content hash (XXH3-64) for files up to 16 MiB; if another program rewrote the file, you are asked "Overwrite / Save as / Cancel".
- **Characters that cannot be represented**: characters that the target encoding cannot represent are shown with their positions before writing, and you choose "Save as UTF-8 / Replace and save". Nothing is silently replaced. Files with invalid bytes show them as `<0xNN>` and are opened read-only.
- **Large files**: shows loading progress with cancel, and stays responsive to input while loading, saving and searching 100 MB files. Files larger than 512 MiB and files with a high ratio of invalid bytes trigger a warning before opening. Files with a line longer than 1 MiB are opened read-only and show the first 64 KiB.
- **Editing**: undo and redo, indentation (Tab / Shift+Tab), paste (control characters in the text are not executed as commands), the system clipboard (Windows).
- **Search and replace**: plain text search (case toggle, count, highlighting of matches, wrap-around), literal replace all (undone with one undo).
- **Command palette** (`F1` / `Ctrl+P`): the list of commands with their keys and argument choices.
- **Japanese user interface**: widths of full-width characters, half-width katakana and emoji, a setting for ambiguous width (1/2), the IME cursor following the caret, the hint bar, confirmation dialogs, and messages (what happened + what to do).
- **Configuration**: 7 items in `config.toml` (tab width, indentation, encoding and line ending of new files, ambiguous width, color depth). Mistakes are reported without stopping startup. An example is the bundled `config.example.toml`.
- **Preparing for abnormal termination**: on panic, closing the console, and Ctrl+Break, unsaved content is rescued together with its line-ending and encoding information (with a free space check), and the next start tells you where it is.
- **Command line**: `--version`, `--help`, `--readonly`, `--encoding`.
- **Distribution**: a Windows x86_64 zip with `SHA256SUMS`, `THIRD-PARTY-NOTICES.md`, `README.md` and `config.example.toml`. The signature verification steps are in `README.md`.
- Development foundations: the specification (`docs/`), CI (fmt, clippy, tests, E2E, dependency checks, `cargo deny`, DCO, gitleaks), `cargo xtask` (check, check-deps, check-dist, dist, gen-notices, bench, i18n and more), and the release procedure (`release.yml`).

### Known limitations

See "Known limitations (v0.1)" in the bundled `README.md`. The main ones: Windows 11 only (Windows 10, macOS and Linux are not supported), only one open document at a time, no regular expression search, the executable is not signed (SmartScreen, Smart App Control), and unsaved content cannot be rescued on forced termination or power loss.

### Fixed

- Bugs found and fixed in pre-release verification: the encoder panicked on ISO-2022-JP control characters; editing a read-only document was silently ignored; files with paths longer than 260 characters could not be saved; saving to a dangling link gave no reason; a rewrite with the same mtime and length was missed on save; opening the search bar stopped screen drawing (Ctrl+F); key input was slow during a full search of 100 MB; DLL search limited to System32 (DLLs in the executable's folder are not loaded; defense in depth); `ui.redraw` (Ctrl+K R) and some default keys (Shift+Enter and Ctrl+H in search, Ctrl+N / Ctrl+P in the palette, and so on) were not implemented.
