### 照合の試作 (eve-core の純粋関数の形)

- 本文の解釈は git の `dir.c` に倣う (UTF-8 の BOM を飛ばす、行末の CR を 1 つ落とす、`#` の行と空行を飛ばす、エスケープされていない末尾の空白を落とす、`!` で否定、末尾の `/` でディレクトリだけ、途中か先頭に `/` があれば置き場所からの相対パスに当て、無ければ名前に当てる)。
- 照合は git の `wildmatch.c` をそのまま写した (パスに当てるときは `WM_PATHNAME`、大文字小文字は区別する)。名前に当てるパターンは、ワイルドカードを含まないもの (完全一致) と `*` + 文字列 (末尾の一致) を先に分ける (git と同じ)。
- 優先: 内側の `.gitignore` から外側へ、最後は `.git/info/exclude`。各ファイルの中は後ろの行から当て、最初に当たったものが決める。除外したディレクトリには降りない。`.git` は常に飛ばす。

```rust
/// ディレクトリごとの除外の連鎖 (内側から外側へ。一番外は `.git/info/exclude`)。
pub struct Chain { rules: Option<Rules>, parent: Option<Arc<Chain>> }

impl Chain {
    pub fn is_ignored(&self, rel: &str, name: &str, is_dir: bool) -> bool {
        let mut cur = Some(self);
        while let Some(c) = cur {
            if let Some(r) = &c.rules && let Some(d) = r.decide(rel, name, is_dir) {
                return d; // 後ろの行から当てて、最初に当たった行の結果 (否定なら false)
            }
            cur = c.parent.as_deref();
        }
        false
    }
}
```

### 走査の試作

- `read_dir(path) -> Vec<Entry { name, kind }>`: `FileSystem::read_dir` に当たる関数。名前と種類 (ファイル・ディレクトリ・その他) だけを返し、追加の `stat` をしない (std の `read_dir` の `file_type()`。Windows は `FindNextFileW` の属性、Linux は `d_type`)。
- 走査の状態 (`Scan`) は、未処理のディレクトリのスタックと、それぞれの除外の連鎖を持つ。1 回のジョブで **ディレクトリを 16 個** 処理し、見つけたファイルを束にして主スレッドへ送り、続きを **自分のレーンのキューの末尾へ積み直す**。

```rust
Job::Scan(mut j) => {
    let done = j.scan.step(dirs_per_step, &mut out); // ディレクトリを dirs_per_step 個処理する
    let _ = main.send(Msg::ScanBatch { chunk: out.into_iter().map(Cand::new).collect() });
    if !done {
        let _ = me.send(Job::Scan(j)); // 続きを自分のキューの末尾へ (間に入ったジョブが先に走る)
    }
}
```

### ファジー照合の試作

- 候補 (`Cand`) は相対パス・ASCII だけを小文字にしたバイト列・名前の開始位置・含む文字の集合 (64 ビット。速い棄却) を持つ。候補は走査の側 (`bg`) で作り、4,096 件前後の不変の塊 (`Arc<[Cand]>`) の列にする (主スレッドは塊の Arc を足すだけ。ファインダのジョブに渡す複製は塊の数だけの Arc の複製)。
- 採点は fzf の v1 に倣う (前から当てて終端を決め、後ろから当て直して最短の窓にし、窓の中を前から採点。語頭・区切りの直後・camelCase の境目・連続・名前の中を加点し、間を減点)。空白で区切った語は AND。上位 100 件を二分ヒープで取る。4,096 件ごとに取消しの印を見る。
- 検索語: 9 語 (`editor`・`mod.rs`・`src/lib`・`c012 handler`・`資料`・`zqx` (一致ほぼ無し)・`fixtures/flat/case12345`・40 文字のパス・`e`) を 1 文字ずつ打った **100 個の検索語** を、それぞれ 30 回 (計 3,000 回)。

### 譲り方の模擬 (固定 2 本)

- `io` と `bg` を 1 本ずつのスレッドにし、それぞれのキュー (mpsc) から先着順にジョブを取る。走査は `bg` で上のとおり積み直す。
- **入力スレッド** が 5〜30 ms の間隔で 1,000 回の打鍵を送る。**主スレッド** は打鍵ごとに模擬の処理 (検索語の 1 文字の追加と、200×50 のセルを埋める決まった量の計算) をし、ファインダの場面では前のファジー照合のジョブを取り消して新しいジョブを `bg` に積む。**打鍵の遅れ** = 入力スレッドが送った時刻から主スレッドが処理を終えた時刻まで (主スレッドで、走査の束・ジョブの知らせ・照合の結果の処理の後ろに待つ時間を含む)。
- **保存・読込のジョブ** を別のスレッドから 20〜80 ms ごとに交互に投入する (保存 = 1 MiB を一時ファイルに書いて `fsync` して改名、読込 = 1 MiB を読む)。**開始の遅れ** = 投入からワーカーが始めるまで。投入先は (a) 走査と同じ `bg` (行の「同じレーン」。譲り方の厳しい形) と、(b) `io` (ADR-0006 の振り分けどおり) の両方。
- 走査は打鍵の間ずっと繰り返す (終われば新しい走査を積む)。

**何を測っていないか**: 実機の端末を通した打鍵の区間 (BM-103b、01 §3.0.1 の (b): 入力のバイトを読んでから `write` + `flush` が戻るまで) は測っていない。ここでの「打鍵の遅れ」は、走査・照合のジョブが主スレッドの処理をどれだけ待たせるかの模擬で、描画と端末の出力の時間を含まない。

- `ignore::WalkBuilder` (`hidden(false)`・`parents(false)`・`ignore(false)`・`git_ignore(true)`・`git_exclude(true)`・`git_global(false)`・`require_git(true)`・`.git` を飛ばす) の `Walk` (1 本) と `WalkParallel` (論理 24 本)。

#### 大文字小文字 (`core.ignoreCase`)

Windows の `git init` は `core.ignorecase = true` を書く。この既定のまま比べると、git は **1,607 件多く除外する** (`FOO.LOG` を `*.log` で、`Notes.BAK` を `*.bak` で、`Build/` を `build/` で除外する)。上の差 0 は `core.ignoreCase=false` での結果。ripgrep (`ignore`) も既定は大文字小文字を区別する。Windows・macOS で git の設定に揃えるか (M31 で決める点の 1)。

| ext4 | 走査 + ジョブを `bg` (区切らない) | **288 ms** | p99 0.213 / 最大 0.290 ms | 284 ms |

- 区切って積み直せば、同じ `bg` に入れたジョブでも開始の遅れは最大 47 ms (前の区切り 1 回 + 前に積まれたファジー照合 1 回 + 前の保存 1 回)。区切らないと走査 1 回分 (0.3〜0.9 s) 待つ。粒度は 1・16・64 個でほとんど変わらない (遅れの上限は 15,000 ファイルのディレクトリ 1 つの `read_dir` で決まる)。ADR-0006 の振り分け (保存・読込は `io`) なら、走査の影響は 0.3 ms 未満。
- この回の走査 1 回の時間 (708〜1,384 ms) は、(3) の回 1 より遅い。`bg` のスレッドが省電力のコアに載った回と、ファインダの照合が同じ `bg` に入る分を含む。
- **主スレッドで候補の一覧を解放すると止まる**: 最初の版は、走査が終わるたびに古い候補の一覧 (106,405 件) を主スレッドで解放していた。この解放が 1 回 13〜15 ms かかり、打鍵の遅れが p99 5.2〜8.5 ms・最大 10.6〜15.0 ms になった (64 個ごとの回は p99 8.48 ms で NFR-103 の p99 8 ms を超えた)。古い一覧を `bg` に送って解放する形にして、上の表の値 (p99 0.14 ms 以下) になった。**主スレッドで大きな一覧を解放しない** ことは、M31 の仕様に書く (下の「M31 の仕様の PR で決める点」の 4)。

## 判定 (S-26 の合否の基準ごと)

## 比べた並列の案 (行の決め方の「(2) か (3) を満たさないとき」)

走査の専用のレーンを `n` 本の自前のプール (共有のスタック + `Condvar`。rayon は使わない) にしたときの時間。`WalkParallel` と交互に 11 回。コアは固定しない。

| 本数 | NTFS (中央値) | `WalkParallel` との比 | ext4 (中央値) | `WalkParallel` との比 |
|---|---|---|---|---|
| 1 | 643 ms | 3.52 | 179 ms | 4.73 |
| 2 | 397 ms | **2.17** | 94.5 ms | **2.50** |
| 3 | 269 ms | 1.47 | 61.7 ms | 1.63 |
| 4 | 213 ms | 1.17 | 47.3 ms | 1.25 |
| 8 | 116 ms | 0.64 | 37.7 ms | 1.00 |
| `WalkParallel` (24 本) | 183 ms | 1 | 37.8 ms | 1 |

- **照合だけを分けて並べる案** は効かない: 照合は全体の約 1 割で、残りは `read_dir` (OS の列挙)。
- **rayon** を足す必要は無い: 自前の 8 本で `WalkParallel` (24 本) より速い。足すなら 02 §13.0 の評価が要る。
- **`bg` を 2 本にする案** は、`bg` のキューの順序 (OQ-198) と、同種の古い要求の取消し (02 §9.1) が 2 本の間で成り立たなくなる。走査だけを分けるなら専用のレーンのほうが影響が狭い。

## OQ-103 の扱い

(3) を満たさないので、行の決め方に従い **確定しない**。10 の OQ-103 を「S-26 の実測」で更新し、次の選択肢と推奨を書いて PO に尋ねる (ADR-0006 の改訂を含むため)。

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| **(A) 推奨** | rayon を入れず固定 2 本のまま。走査は `bg` でディレクトリ 16 個ごとに積み直して譲る (ADR-0006 を改めない) | (1)(2)(4) は満たす。走査は 10 万ファイルで 0.36〜0.77 s (温まった NTFS)・0.17 s (ext4) で、候補は束ごとに届くのでファインダは走査の途中から使える。作業スレッドの規則 (02 §4.3 R11) と決定的な試験 (`ManualJobSpawner`) を変えない | (3) の 3 倍を、`bg` が省電力のコアに載ると超える (3.5 倍)。初回 (冷えた状態) は未測定で、並列の差はそこでもっと開く恐れがある |
| (B) | ワークスペースの走査の間だけ、走査の専用のレーンを自前で 2 本足す (終われば終わる。ADR-0006 の改訂。`bg` は変えない) | NTFS で 2.2 倍・ext4 で 2.5 倍になり (3) を満たす | スレッドの規則の例外がまた増える (標準入力の 2 本に続く)。走査の順序が決まらないので、結果の並べ直しと、取消し・上限 (20 万件) を 2 本の間で揃える作業が要る。`ManualJobSpawner` での試験の形を考え直す |
| (C) | (B) を 4 本にする | 1.2 倍 | (B) の短所に加えて、ノート PC で I/O と CPU を多く使う |

**推奨は (A)**。理由: 差は「1 本で OS の列挙を待つ」ことから来ていて、自作の部分を速くしても縮まらない一方、絶対の時間は小さく、譲り方 (4) は満たしている。(3) の不合格はコアの種類 (高性能のコアなら 2.0 倍) によるもので、基準機でも同じかは未測定。**(A) を採るときの条件**: 基準機 (と、可能なら OS の再起動の直後) で (3) を測り直し、M31 の BM (ファインダの走査の時間・横断検索の時間) で走査が遅いと分かったら (B) に切り替える。`JobSpawner` の形は変えないので、後から (B) に差し替えられる (02 §9.1)。

反対の論点: 合否の基準 (3) は M28 で決めたもので、(A) はそれを満たさないまま採ることになる。省電力のコアを持つ CPU (ノート PC と、近年のデスクトップ) では、`bg` がそこに載るのが普通の状態とも言える。横断検索 (FR-405) はファイルの中身を開いて読む費用が走査より大きく、そこでは 1 本の差がさらに効く (S-26 では測っていない)。

## M31 の仕様の PR で決める点

1. **大文字小文字**: git に合わせて `core.ignorecase` (Windows・macOS の `git init` の既定は `true`) を読むか、ripgrep の既定どおり区別するか。区別すると、`*.log` で除外したつもりの `FOO.LOG` がファインダと横断検索に出る (この木で 1,607 件)。**推奨**: リポジトリの `core.ignorecase` を読んで揃える (読めなければ OS の既定。Windows・macOS は区別しない)。読むのは `.git/config` の 1 行だけで、グローバルの設定は読まない。
2. **POSIX の文字の集合** (`[[:digit:]]` など): 自作は git と同じに解釈した (`ignore` の globset は違う)。仕様に「git の wildmatch に揃える」と書き、差分試験の木に入れる。
3. **区切りの単位**: ディレクトリ 16 個ごとで足りる (1・16・64 個で開始の遅れの最大はほぼ同じ 25〜28 ms)。遅れの上限は大きなディレクトリ 1 つの `read_dir` で決まる (15,000 ファイルで 11〜31 ms)。10 万を超える 1 つのディレクトリでは 100 ms に近づき得るので、**1 つのディレクトリの中でも項目の数 (案: 4,096) ごとに区切る** か、上限 (FR-125 AC-3) で打ち切るかを決める。
4. **候補の一覧の持ち方と解放**: 主スレッドで 10 万件の一覧を解放すると 13〜15 ms 止まった。一覧は不変の塊 (`Arc<[Cand]>`) の列で持ち、作り直したときの古い一覧は `bg` に送って解放する (または最後の参照をジョブが持つ形にする)。
5. **ファインダの照合と保存の順**: 保存・読込は `io` に置く (ADR-0006 どおり)。`bg` に置くと、ファジー照合 1 回と走査の区切り 1 回の後ろに待つ (最大 47 ms)。
6. **項目の数の上限** (案: 20 万) と、上限に達したときの表示。この木 (残るファイル 10.6 万) では、候補の用意 23.8 ms・照合の p99 10 ms で余裕がある。

## 反対の論点

- **(A) は基準 (3) を満たさないまま採る案**。M28 で決めた基準を、結果を見てから緩める形になる。(3) の目的は「1 本では遅すぎないか」を見ることで、絶対の時間 (0.4〜0.8 s) と譲り方 (4) を合わせて判断した、というのが推奨の理由だが、PO が基準どおり (B) を選ぶ余地を残した。
- **固定しない測り方は再現しにくい**。同じ条件の 21 回の中でも 1.9〜4.7 倍にばらついた。コアを固定した値 (2.0 倍・3.5 倍) は再現したが、実際の製品の `bg` は OS が載せる先を決める。
- **ファジー照合の採点は fzf の v1 の簡略な形**。最適な一致を探す採点 (fzf の v2・nucleo) より速いが、順位の質は M31 の仕様の PR と実際の使用で確かめる。大文字小文字の畳み込みは ASCII だけ (日本語には大文字小文字が無いが、ラテン文字の拡張は畳まない)。
- 時間は開発機 1 台の値で、同じ時間帯に他のアプリが動いていた。`C:` の木は Defender のリアルタイム保護の対象 (既定) のまま。
