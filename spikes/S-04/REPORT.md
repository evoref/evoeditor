## 候補の方式

eve-core からは ropey が見えない (`TextStorage` が隠す) ので、どの方式も `TextRead` の `chunks` / `chunk_at` の上で動かした。

| 方式 | 中身 |
|---|---|
| (a) regex-cursor | `regex_cursor::Cursor` を `TextRead` の上に自前で実装した (`TextCursor`。進む・戻るは `chunk_at` で引く。約 40 行)。`ropey` feature は使わない (`default-features = false, features = ["perf-inline"]`) |
| (a') regex-cursor の前段の絞り込みを切る | (a) に `Config::auto_prefilter(false)` を付けたもの (下の不具合の退避策) |
| (b) regex-automata の遅延 DFA を直接 | `hybrid::dfa::DFA` を前向き (leftmost-first) と後ろ向き (anchored、`MatchKind::All`) で作り、チャンクの上を 1 バイトずつ自前で回す (位置だけ。キャプチャは一致の範囲を複写して取り直す想定) |
| (c) 全文連結 | `chunks` で全文を 1 本の `String` に複写し、`regex::Regex::find_at` で探す (比べる相手) |
| (d) 行の窓 | パターンの HIR から「一致が含みうる `\r` / `\n` のバイトの数の上限 k」を求め、**1 MiB の核 (行の境界に揃える) + その後ろ k 行** を 1 本に複写した窓で探す。核の中で始まる一致だけを採り、次の窓へ進む。窓の前後に 1 文字の文脈を付け、`regex_automata::meta::Regex` の `Input::span` で走査の範囲だけを限る (`^` `$` `\b` `\A` `\z` の判定を全文と揃える)。k に上限が無いパターン (`(?s).*`、`\s+`、`[^a]+` など) は (c) に落とす |
| (行単位) | 今の経路 (`eve_core::scan_bytes` → `LineScan`)。1 行で済むパターンの比べる相手。BM-109r と同じ経路 |

どの方式も、一致の選び方は eve-core の `find_in_line_inner` と同じ「製品の走査」にそろえた (空の一致は採らずに 1 文字進める・両端が書記素境界でない候補は捨てて次の char 境界から探し直す・採ったら終端から続ける)。検索語には 03 §12.3 のフラグ (`m`・`R`) と `\n` の糖衣 (文字クラスの外の `\n` を `(?:\r?\n|\r)` に書き換える) を掛けた。

## (1) 正しさ: 全文連結の `regex` との差分 fuzz

手順: 乱数で文書 (ASCII・`é` と `e` + U+0301・`日本`・`😀`・`σ Σ ς`・`ſ`・U+212A・タブ・LF・CR・CRLF を混ぜる。2 割は 300〜2,800 文字にしてチャンクを複数にする) とパターン (固定の 70 個 + 文法から作る乱数のパターン) とフラグ (`(?i)` を 1/3、`m` を 7/8、`R` を 4/5、`\n` の糖衣を 1/2) を作り、全文連結の `regex` の結果と比べた。パターンの部品は、キャプチャ・名前付きキャプチャ・`^` `$` `\A` `\z` `(?-m:^)`・`\b` `\B`・`\w` `\d` `\s` `\pL` `\p{Han}`・`(?i:..)`・`(?s:.)`・否定のクラス・`\n` `\r` `\r\n`・空になりうる繰り返し・最短一致を含む。チャンクの分け方は 2 通り: (i) char 境界で乱数で分ける (CRLF の間でも分ける)、(ii) `eve_text::Text` を先頭への挿入の繰り返しで作り (1/3 は `Text::from`)、その木のチャンクの上の `TextCursor` で走る。

各 10 万件 (2 つの種。どちらも release ビルドで 1 回ずつ):

|---|---|---|

**regex-cursor 0.1.5 の不具合 (既定の設定)**: 前段のリテラルの絞り込み (prefilter) が、チャンクの境目の近くで一致を取りこぼす・短く切る。`auto_prefilter(false)` にすると 0 になるので、原因は prefilter の経路 (`src/literal.rs` の `find_n`。チャンクをまたぐ複数リテラルの処理) と見ている (修正は試していない)。最小の例 (貪欲に縮めたもの):

- 03 §12.3 の糖衣そのもの `\r?\n|\r` で、チャンクが `["k", "\r\nk\n\n"]` のとき: `regex` は `(1,3) (4,5) (5,6)`、regex-cursor は `(1,2) (2,3) (4,5) (5,6)` (CRLF を 2 つの一致に分ける)。
- `K?(?:\r?\n|\r)` で `["\n\n", "\n"]`: `regex` は `(0,1) (1,2) (2,3)`、regex-cursor は `(0,1) (2,3)` (取りこぼす)。
- **実際の `eve_text::Text` でも起きる**: 挿入で作った 1,004 バイトの文書で、チャンクが `[0, 503)` と `[503, 1004)` に分かれ、2 つ目のチャンクが CRLF で始まるとき、`(?:\r?\n|\r)` に対して `regex` は `(503,505)`、regex-cursor は `(503,504)` を返した (ropey は CRLF をチャンクの間で分けないが、チャンクの先頭に置くことはある)。

**追試 (別の種で 1 回。2026-11-11)**: `fuzz 20000 777` でも同じ傾向だった。(d) 行の窓は 15,477 件で不一致 0、regex-cursor の既定の設定は任意の分け方で 123 件・`Text` の木で 4 件の不一致。`repro_text` (実際の `Text` の上の再現) も、同じ結果 (`(503,505)` が `(503,504)` になる) を返した。

**後ろ向きの検索**: どの方式にも「前の一致」を直接引く API は無い (leftmost-first の左からの非重複の列は、走査を始める位置で変わる)。

- **厳密**: 文書の先頭から前向きに走査し、`from` より前で終わる最後の一致を採る。今の `find_next` (単発のジョブ) がこの形で、どの方式でもそのまま使える。費用は全件の走査と同じ。
- **窓で速くする**: `from` の行から w 行前の行頭から前向きに走査し、無ければ w を倍にする (今の `sync_find` の後ろ向きと同じ形)。1 行で済むパターンでは厳密と同じになるが、**複数行のパターンでは厳密と食い違うことがある**: fuzz で種 101 は 42,805 件中 1,077 件 (約 2.5%)、種 202 は 42,928 件中 1,095 件。例: `[^a](?:\pL)*(?:\r?\n|\r)` を `"\nB\r\t_A"` で `from = 5` のとき、厳密は `(0,3)`、窓は `(1,3)`。乱数のパターンは食い違いが起きやすいものに偏っているので、実際の頻度はこれより低いと見ている (推測)。この比較は全文連結の `regex` で行ったので、方式に依らない意味の差である。

**`\n` の糖衣との両立**: 糖衣は検索語の書き換えなので方式に依らない。糖衣を掛けた半分の件数を含めて (a')・(b)・(d) は不一致 0。(a) は糖衣の形 (`\r?\n|\r`) で上の不具合に当たる。

## (2) 性能

文書は `bm_109.rs` の `corpus` と同じ作り方 (平均 80 B の行、ASCII と日本語)。100 MB (行の区切りは LF) と 10 MB の 1 行 (区切りは空白)。`Text::from` で読み込んだ形の木。全件の走査は、上の「製品の走査」で全件を数え終えるまで。最初の一致は文書の先頭から最初の一致を採るまで。

### NFR-103 への影響

検索は `bg` のワーカーのジョブで走り (03 §12.2)、どの方式もメインスレッドでは動かないので、影響は CPU・メモリ帯域・確保の競合だけと見込む。**NFR-103 の計測区間 (09 の BM-103b-search) は測っていない**。代わりの目安として、別スレッドで 100 MB の検索 (`abcdef\n\d+ 日本語`) を繰り返しながら、メインスレッドで「1 MB の `Text` に 1 文字挿入して行の位置を引き、Snapshot を作る」処理を 1 ms ごとに 2,000 回測った (1 回):

| 背景の負荷 | p50 (µs) | p99 (µs) | 最大 (µs) |
|---|---|---|---|
| なし | 0.5 | 1.3 | 56.7 |
| (a) regex-cursor | 1.2 | 11.0 | 49.2 |
| (c) 全文連結 | 1.8 | 12.1 | 58.5 |
| (d) 行の窓 | 1.9 | 11.1 | 176.0 |

p50 / p99 の増え方は NFR-103 の目標 (p50 2 ms / p99 8 ms) より 2 桁以上小さい (最大は (d) の 176 µs。最大は 1 回ずつの計測なので揺れが大きい)。(c) は検索ごとに文書と同じ大きさの確保をする (100 MB で 100 MiB) ので、メモリの余裕の少ない環境では別の問題になりうる (未計測)。取り消しの間隔は、(d) は窓 (1 MiB) ごとに確認でき、(a) は一致と一致の間でしか確認できない (一致の無い 100 MB を 1 回の `search` で走り切る。`Cursor::advance` で取り消しを見て `false` を返す工夫は可能だが未検証)。

## 退路 (S-04 の行の最後の列) が成り立つか

「小さい文書は全文連結、大きい文書は複数行パターン非対応のまま」は成り立つ: (c) は正しさの基準そのもので、100 MB でも確保と複写は 18〜19 ms・100 MiB だった。(d) を採る場合も、k に上限の無いパターンの扱いとしてこの退路をそのまま使える。

## 結論

1. **勧める方式は (d) 行の窓**。合否の基準の 3 項目を満たした唯一の方式: 差分 fuzz の不一致 0 (k に上限の無いパターンは (c) に落とすので基準と同じ)、1 行で済むパターンは行単位の 0.20〜0.87 倍、複数行は全文連結 (連結を含む) の 0.55〜1.11 倍、新しい依存なし。`scan_bytes` の中の `StreamScan` として足せ、`TextStorage` の公開 API も変えない (03 §12.3)。
2. **(a) regex-cursor 0.1.5 は既定の設定で正しさの基準を満たさない** (prefilter の不具合。03 §12.3 の糖衣 `\r?\n|\r` で起き、実際の `Text` のチャンクでも再現)。prefilter を切る (a') は不一致 0 だが、10 MB の 1 行の複数行のパターンで全文連結の 3.8〜3.9 倍になり性能の基準を満たさない。保守も止まっている。
3. (b) は遅延 DFA が扱えないパターン (Unicode の `\b` と ASCII 以外の文字など) で約 18% が quit し、前段の絞り込みも無いので 2〜7 倍遅い。regex-cursor と同じものを自前で作ることになる。
4. 比べる相手の解釈: 「全文連結の方式」を **連結を含む** 時間と読んだ。連結済みの文字列の検索だけと比べると、一致の無い・少ないパターンで (a)・(d) とも 2 倍を超える (100 MB の `\n\n` で (d) は 4.3 倍、10 MB の 1 行の `abcdef\n\d+ 日本語` で 2.75 倍)。この読み方でよいかは人間が判断する。

### 実装の前に決めること

1. 複数行の実行に入る条件: 検索語が `\n` (または `\r`) を明示したときだけにするか (それ以外は今の `LineScan` のまま。v0.2 の意味が変わらない)、常に複数行で走らせるか。
2. 否定のクラス (`[^"]`)・`\s`・`\W` が行の終端に一致するか。`regex` の既定では一致するので、常に複数行で走らせると `"[^"]*"` が行をまたぐ (v0.2 の行単位とは結果が変わる)。また、これらは k を上限なしにする。明示の `\n` だけが行の終端に一致するよう HIR を書き換える案 (ripgrep の既定に近い) なら k はほぼ常に有限になる。
3. k に上限の無いパターンの扱い: (c) に落とす (文書の大きさの上限を決める) / 「未対応」と出す / 1 つの一致がまたぐ行の数に上限を設ける。
4. 糖衣の範囲: 文字クラスの中の `\n` (`[\n]`・`[^\n]`) は書き換えられない (`[^\n]` は CR に一致する)。明示の `\r\n` は `\r(?:\r?\n|\r)` になり、CR CR にも一致する。
5. 後ろ向き (前の一致) の意味: 厳密 (全体の走査、O(n)) と、窓で近似 (今の `sync_find` の形、上の 2.5% の差) のどちらを仕様にするか。
6. 範囲 (`scan_bytes` に渡す範囲・選択範囲内) の端で、窓が k 行はみ出して読んでよいか。範囲の境界をまたぐ一致は今は採らない (§12.5) ので、それに揃えるか。
7. 可視範囲のハイライト (§12.2): 可視行より上で始まる複数行の一致を出すか (出すなら k 行前から探す)。単語単位 (§13.3) の検査は今は行の文脈 (`word_boundaries(line)`) なので、一致の端の文脈を窓から取る形にする。置換のキャプチャは窓の文字列の上で取れる (スパイクでは未実装)。
8. `regex-automata` を eve-core の直接の依存にするか (`Input::span` を使うため。crate の数は増えないが deps-policy の許可が要る)。`regex::Regex::find_at` と、窓の後ろに 1 文字の文脈を付けるだけで足りる見込みだが未検証。
9. 窓の核の大きさ (1 MiB) と、取り消しの確認・最初の一致 (カーソル位置から前方、§12.2) の送り方。

### スパイクのコードの要点

`TextRead` の上の `Cursor` (方式 (a)):

```rust
impl regex_cursor::Cursor for TextCursor<'_> {
    fn chunk(&self) -> &[u8] { self.chunk.as_bytes() }
    fn advance(&mut self) -> bool {
        let next = self.off + self.chunk.len();
        if next >= self.len { return false; }
        let (c, s) = self.text.chunk_at(ByteOff(next)); // その位置で始まるチャンク
        self.chunk = c; self.off = s.0; true
    }
    fn backtrack(&mut self) -> bool {
        if self.off == 0 { return false; }
        let (c, s) = self.text.chunk_at(ByteOff(self.off - 1));
        self.chunk = c; self.off = s.0; true
    }
    fn total_bytes(&self) -> Option<usize> { Some(self.len) }
    fn offset(&self) -> usize { self.off }
}
```

一致が越えうる行の終端のバイトの数 (方式 (d) の k。`\r\n` は 2 と数えて多めに見積もる):

```rust
match h.kind() {
    HirKind::Empty | HirKind::Look(_) => Some(0),
    HirKind::Literal(l) => Some(l.0.iter().filter(|&&b| b == b'\n' || b == b'\r').count()),
    HirKind::Class(c) => Some(usize::from(class_has_nl(c))), // `\r` か `\n` を含むクラス
    HirKind::Repetition(r) => {
        let n = max_newlines(&r.sub)?;
        if n == 0 { Some(0) } else { r.max.map(|m| m as usize * n) }
    }
    HirKind::Capture(c) => max_newlines(&c.sub),
    HirKind::Concat(v) => v.iter().try_fold(0, |a, h| Some(a + max_newlines(h)?)),
    HirKind::Alternation(v) => v.iter().try_fold(0, |a, h| Some(a.max(max_newlines(h)?))),
}
```

窓 (方式 (d)): 核の終わり `core_end` は「核の始まり + 1 MiB」を含む行の次の行頭、窓の終わり `ext_end` はその k 行後ろの行頭。窓 `[hs, he)` は前後に 1 文字の文脈を足して (大きさを先に確保して) 複写し、`Input::new(&buf).span(pos - hs .. ext_end - hs)` で探す。核の中で始まる一致は k 個より多くの終端を越えられないので必ず窓に収まり、leftmost-first の選び方も全文と同じになる。核の中で見つからなければ、次に探す位置は `max(pos, core_end)`。
