## 1. ビジョン

> **「どの OS のターミナルでも一瞬で起動し、巨大なファイルでも固まらず、データを絶対に失わない。
> その同じ中核 (core) の上で TUI を完成させ、AI 支援を安全に載せられるテキストエディタ」**

evoeditor は Rust 製のテキストエディタである。最初は「nano より少し賢く、起動と応答が速く、日本語を正しく扱える」最小限の TUI エディタ (v0.1。Windows 11 版・単一文書・UI は日本語、[01 §4.1](01-requirements.md#41-v01-の定義)) として **できるだけ早く世に出し**、段階的なリリース (v0.2 → v0.3 → v0.4 → v1.0) で機能を足していく ([ADR-0028](10-decisions.md#adr-0028-リリース最優先の段階リリース))。設計の最初から次の将来像を織り込む。

1. **TUI を完成させる**: TUI は第一級のまま継続的に進化させる。1.0 は TUI のみで出す。**TUI と core (公開リポジトリ) は OSS、ライセンスは Apache-2.0 単独** (ユーザー回答で確定、[ADR-0038](10-decisions.md#adr-0038-公開-crate-の外部の消費者と寄稿の方針))、寄稿は **DCO** (いずれもユーザー回答で確定)。公開 crate は外部の消費者 (駆動 API のクライアント等) から使われ得るため、境界型は契約版で管理する ([12-licensing-distribution](12-licensing-distribution.md))。境界 (`eve-host` / `Frontend` trait / 境界型の契約) は v0.1 から用意する。core は端末に依存しない「ヘッドレスなエディタエンジン」とする。
2. **AI/LLM 連携 (ローカル LLM を一級市民に)**: LLM による編集支援・補完を 1.0 以降に追加する。**自分のマシンで動くローカル LLM (llama.cpp の `llama-server` 等) をクラウドより先に・深く** 連携し (サーバの能力・トークナイザ・プロンプトキャッシュ・FIM・文法制約まで使う)、ネットワークが無くても完結させる ([ADR-0034](10-decisions.md#adr-0034-ローカル-llm-を一級市民とする接続方式))。AI はユーザーと同じ「コマンド」と「承認」の経路を通ってのみ文書を変更でき、送信先と送信内容はユーザーが制御する。
3. **AI と一緒に作りやすい構成**: 仕様・コード・テストを機械的に結び、ヘッドレスで検証できる構造にして、AI コーディング支援と人間が並行して開発できるようにする ([ADR-0033](10-decisions.md#adr-0033-ai-連携に適した開発構成))。外部のツールや AI エージェントがエディタを操作するための駆動 API も同じ基盤の上に置く。

## 2. 目標 (Goals)

| ID | 目標 | 判定の目安 (詳細値は 01 の NFR) |
|---|---|---|
| G1 | **軽量・高速・低メモリ** | 起動・キー入力応答・巨大ファイルの各数値目標 ([01 §3.1](01-requirements.md#31-性能-performance-nfr-1xx)) と、アイドル時・ファイルを開いた時・Undo 履歴のメモリ上限 ([01 §3.2](01-requirements.md#32-資源-nfr-2xx)、NFR-201〜203) を満たす |
| G2 | **データ保全** | 保存時のクラッシュ・電源断でも元ファイルが壊れない。パニック・端末クローズ (Windows のコンソールクローズ)・シグナル (macOS / Linux を出荷する版) のときは未保存変更を緊急退避 (v0.1)。SIGKILL・OOM・電源断を含む復旧はスワップで (v0.2 の最優先)。v0.1 の制約の扱いは [OQ-42](10-decisions.md#oq-42-v01-の非パニック異常終了への備え) |
| G3 | **クロスプラットフォーム** | Windows / macOS / Linux で同一の操作体系・同一の設定ファイルが動く。**v0.1 は Windows 11 (Windows Terminal・conhost) だけを出荷** し、macOS / Linux は v0.2 で出荷する (確定 (ユーザー回答)、OQ-15。実機で確認する手段の確保が前提)。Windows 10 は公式には対応しない (01 §4.3)。core は OS 非依存を保ち、CI で Linux のビルドとテストを続けて移植性を守る (01 NFR-401、02 §4.7) |
| G4 | **core / frontend の厳密分離** | core は端末ライブラリに依存せず、ヘッドレスでテスト・駆動できる。TUI と駆動 API・テストが同じ境界型を消費する |
| G5 | **段階的拡張とリリース優先** | 最小核を早く出し、版ごとに機能を足しても既存の設計 (公開面) を壊さない |
| G6 | **初心者にも上級者にも** | 初見でも画面のヒントだけで保存・終了できる。上級者はキーマップ・設定で最適化できる。色だけに頼らない表示 (NFR-604) とチョードの時間切れなし (02 §7.2 K2) は v0.1 から。スクリーンリーダー配慮モードは v0.4 |
| G7 | **安全な AI 連携の土台** | AI による変更は必ず差分提示→承認を経る (インライン補完では、全文が見えている仮想テキストを明示キーで採用することを承認とみなす)。送信内容と送信先 (ローカルでもホスト・ポート) はユーザーが確認・制限できる。ローカル LLM だけで AI 機能が完結し、ローカル LLM の接続は既定でループバックに限る |
| G8 | **国際化されたテキスト処理** | 日本語 (全角・結合文字・絵文字・IME)・レガシー文字コード (Shift_JIS・EUC-JP・ISO-2022-JP。v0.1 から読み書き) を正しく扱う |
| G9 | **既定から美しく読める表示** | 既定テーマは TrueColor で設計し、256 / 16 色・無色の端末でも区別を失わずに縮退する ([ADR-0027](10-decisions.md#adr-0027-既定テーマは-truecolor縮退段を明示する))。v0.1 は truecolor と無色を明示し、256 / 16 色は自動近似で、区別は記号・属性で保つ |
| G10 | **安定性** | 外部入力 (ファイル・設定・端末入力) でパニックしない (NFR-305、fuzz)。長時間 (8 時間) の連続編集でメモリと入力遅延が劣化しない (NFR-306、v1.0 のゲート)。異常終了しても端末を復元し未保存の内容を退避する (NFR-302) |

## 3. 非目標 (Non-Goals)

明示的に「やらない」こと。将来の再検討は妨げないが、設計上これらを前提にした複雑化はしない。

| ID | 非目標 | 理由 / 補足 |
|---|---|---|
| NG1 | フル機能 IDE (デバッガ、ビルドシステム統合等) | 軽量性と矛盾。LSP 連携 (v1.L) までに留める |
| NG2 | Vim / Emacs の完全互換 | 部分的な Vim 風キーマップは Could 扱い ([OQ-02](10-decisions.md#oq-02-デフォルトのキーバインド体系)) |
| NG3 | リアルタイム共同編集 (CRDT/OT) | 需要に対しコスト過大。ただし Transaction 設計は将来の拡張を妨げない形にする |
| NG4 | 組み込みターミナルエミュレータ | 端末の中で動くエディタであり不要。AI の CLI エージェントも端末埋め込みではなく ACP / MCP 等のプロトコルで連携する |
| NG12 | エディタのプロセス内での LLM 推論 | ローカル LLM は外部のサーバ (`llama-server` 等) と HTTP で連携する。推論エンジンをエディタに組み込まない (軽量性・安定性、[ADR-0034](10-decisions.md#adr-0034-ローカル-llm-を一級市民とする接続方式)) |
| NG5 | リモート編集 (SSH 越しのファイル操作) | 当面は「リモート先でエディタ自体を起動」で代替 |
| NG6 | Web / ブラウザ版フロントエンド | ViewModel の設計上は不可能ではないが計画しない |
| NG8 | テレメトリ・利用統計の送信 | 一切行わない (ADR-0019) |
| NG9 | v0.x でのプラグイン機構 | 拡張点 (コマンド登録・イベント・駆動 API) だけ用意し、外部プラグインは v1.X |
| NG10 | バイナリエディタ (hex 編集) | バイナリファイルは検出して警告・読み取り専用で開くのみ |
| NG11 | BiDi (双方向テキスト) のレイアウト | 論理順で表示するのみ (確定 (ユーザー回答)、[OQ-39](10-decisions.md#oq-39-bidi-を非目標-ng11-にするか)) |

## 4. 設計原則 (優先順位付き)

原則同士が衝突した場合は **番号の小さい方を優先** する。各設計判断 (ADR) はどの原則に基づくかを明記する。

| 優先 | 原則 | 意味 | 衝突時の例 |
|---|---|---|---|
| P1 | **データを失わない** | 保存は原子的に。エンコーディング変換で情報が落ちるなら必ず警告。クラッシュ時も復旧手段を残す | 高速化のために fsync を省略しない (性能 < 保全) |
| P2 | **ユーザーの同意なく外へ出さない** | ネットワーク通信・AI 送信・外部プロセス実行はすべて明示的な設定と承認が前提 | AI の利便性より送信前確認を優先 |
| P3 | **UI を止めない** | UI スレッドで I/O・重い計算をしない。重い処理は中断可能なバックグラウンドジョブにする | 機能が遅れて表示されても入力応答を優先 (シンタックス色付けは後から) |
| P4 | **core はフロントエンドを知らない** | core は端末・OS API に直接依存しない。全操作は Command として表現する | TUI だけで楽に書ける近道でも、core に端末概念を入れない |
| P5 | **小さく始め、拡張点だけ先に決める** | 初期の版では使わない機能を実装しないが、後から足す場所 (trait・ID 空間・プロトコル・ファイル形式) は先に定義する。**公開面は早く決め、内部構造は最小にする** | 汎用プラグイン API を先に作り込まない |
| P6 | **どの OS でも同じ体験** | 設定・キーマップ・挙動は OS 間で一致させ、差異は platform 層・frontend 層に閉じ込める | OS 固有の便利機能は platform 層の任意機能として扱う |
| P7 | **発見しやすさ** | 主要操作は画面上のヒント・コマンドパレットから辿れる。隠しコマンドを作らない | 上級者向けショートカットよりも初見で迷わない既定値を優先 |
| P8 | **依存は少なく、理由を持って選ぶ** | 新規依存は採用理由・代替案・ライセンス・メンテ状況を ADR またはチェックリストに記す | 便利でも重い依存 (起動時間・バイナリサイズ悪化) は避ける |

## 5. 想定ユーザー (ペルソナ)

| ID | ペルソナ | 主なニーズ | 設計への影響 |
|---|---|---|---|
| U1 | **ターミナル常駐の開発者** (SSH 先のサーバ、コンテナ内でも作業) | 即起動、軽さ、設定ファイル 1 つで全環境再現、マウスなしでも完結 | 起動時間・依存の少なさ・単一バイナリ配布 |
| U2 | **初心者 / たまにしか端末を使わない人** | Ctrl+S で保存、Ctrl+Q で終了、と画面を見ればわかる | モードレスの既定キー、常時表示のヒントバー |
| U3 | **日本語ユーザー** (レガシー資産で Shift_JIS / EUC-JP / ISO-2022-JP (メール等) / CRLF を扱う) | 文字化けしない、全角幅が崩れない、IME で普通に入力できる | encoding_rs、表示幅計算、IME 位置の追従 |
| U4 | **大きなログ / データを覗く人** | 数百 MB の CSV/ログを開いて検索したい | ropey、遅延処理、巨大ファイル時の機能縮退 |
| U5 | **AI 支援を使いたい開発者** (ローカル LLM を中心に、クラウドも) | 自分のマシンの `llama-server` 等で、選択範囲を指示で書き換えて差分で確認・採用し、入力中に補完を受ける。コードを外へ出したくない / オフラインでも使いたい | ローカル LLM の一級対応 (能力検出・キャッシュ再利用・FIM・構造化出力)、Proposal/承認フロー、ループバック既定、秘密情報除外 |
| U7 | **自動化・AI エージェントの利用者** (スクリプト・CI・AI コーディングエージェント) | エディタを外から決定的に操作し、文字コード安全な編集・原子的保存を使いたい | シナリオ DSL、駆動 API (ヘッドレス)、`Query` / `EditorEvent` |

## 6. 用語集 (Glossary)

以降の全仕様書はこの定義に従う。新しい用語を導入する文書は本表に追記すること。型名の **定義の正本** は [README の正本マップ](README.md#4-正本マップ) に従う (本表の列挙は例示を含む)。

### 6.1 全体・構造

| 用語 | 英語 / 型名 (案) | 定義 |
|---|---|---|
| core | `eve-core` | UI 非依存のエディタエンジン。文書・選択・Undo・コマンド実行・キーマップ解決・ViewModel 生成を担う |
| フロントエンド | frontend | core を駆動し、入力を集めて描画する層。TUI (`eve-tui`)。`eve-host` の `Frontend` trait を実装する |
| Host | `eve-host` | バイナリ (`evoeditor`) の Composition Root。設定読込・Ports 注入・ワーカー・受信口・メインループ・Effect の実行・緊急退避・シグナル・ログを受け持つ (02 §9.2) |
| Frontend trait | `Frontend` | frontend が実装する Host とのインターフェース (能力の申告・入力の開始・描画・Effect・復元)。正本は 02 §9.2 |
| Port | port (trait) | core が定義し外側 (eve-platform 等) が実装する差し替え点 (`FileSystem`, `Clock`, `JobSpawner` 等)。trait の正本は 02 §4.4/§4.5。I/O を伴う Port はジョブ内からのみ呼ぶ。trait は最初の利用者と同時に定義する |
| サービス | service | 長寿命の非同期処理 (LSP・AI)。core とは submit/cancel とメッセージでやり取りする (`LanguageService`, `AiService`) |
| テキストストレージ | `TextStorage` | 文字列データ構造 (rope) の抽象。実装は ropey ([ADR-0004](10-decisions.md#adr-0004-テキストバッファのデータ構造)) |
| バッファ / 文書 | `Document` | 1 つのテキスト内容 + メタデータ (パス、文字コード・BOM・改行の形式 `TextFormat`、履歴、読み取り専用の理由)。ファイルと 1:0..1 対応 |
| ビュー | `View` | 1 つの Document を表示する窓。スクロール位置・選択・折り返し設定を持つ。1 Document に複数 View 可 (分割は v0.4) |
| ペイン / レイアウト | `Pane` / `Layout` | 画面分割の論理構造 (分割ツリー、v0.4)。**分割ツリーとペインのセル矩形は core** が計算し、クローム (ステータスバー・ヒントバー・検索バー) とパネルの配置は frontend が決める |
| 画面 (Window) | `Window` / `WindowId` | Frame を生成し入力を受ける単位 (`Editor::frame(window)` / `handle_input(window, …)`、02 §5.4)。TUI では端末の画面全体に当たり、OS のウィンドウではない。v0.x は 1 つ |
| エディタ状態 | `EditorState` | 全 Document・View・レイアウト・レジスタ・モード等、core が持つ状態の全体。メインスレッドが単独所有 |
| 版 | v0.1〜v1.0、v1.L、v1.X | リリースの単位。v0.1 = 最小核、v0.2 = 日常の不足、v0.3 = 日本語と巨大ファイルの完成、v0.4 = 実用化、v1.0 = 安定化 (TUI のみ)、v1.L = 言語支援・AI 基盤 (ローカル LLM 先行)、v1.X = 拡張。正本は 08 |
| MVP / 最小核 | v0.1 | 最初のリリースの範囲。[01 §4](01-requirements.md#4-mvp-v01-の範囲と段階リリース) で定義 |
| TUI 完成 | — | TUI の完成の定義。**v1.0 のリリース + 重大不具合ゼロ** (確定、08 §8.1、OQ-151。「重大不具合」の判定基準の細目は提案中) |
| 公開 crate / 外部の消費者 | public crates / external consumers | 公開リポジトリで OSS (Apache-2.0 単独) にする crate (core・TUI・ヘッドレス) と、それを版指定で使う外部の消費者 (駆動 API のクライアント等) (ADR-0038、12 §4)。外部の消費者が依存してよい範囲と互換の規則は 12 §4 |
| 公開面 | public surface | 利用者・外部に見え、後から変えると互換性を壊すもの (CommandId、設定キー、キーマップ書式、テーマのロール名、退避ファイルの形式、境界型)。v0.1 で形を決める (ADR-0028) |

### 6.2 テキスト・編集

| 用語 | 英語 / 型名 (案) | 定義 |
|---|---|---|
| 位置 | `Pos` | 文書内の位置。正準表現は **UTF-8 バイトオフセット** ([ADR-0010](10-decisions.md#adr-0010-位置の正準表現)) |
| 範囲 / 選択 | `Range` / `Selection` | `anchor` と `head` の 2 点で表す範囲。`Selection` は 1 個以上の Range (複数カーソル対応。v0.1〜v0.3 は 1 個に制限、複数カーソルは v0.4)。データと写像は eve-text |
| カーソル | cursor | Range の `head`。anchor == head の Range は「選択なしのカーソル」 |
| 書記素 | grapheme cluster | ユーザーが 1 文字と認識する単位 (Unicode UAX #29)。カーソル移動・削除の最小単位 |
| 桁 | column | ステータスバー・`path:行:桁` の桁。単位は書記素数・1 始まり。設定で表示列に切り替えられる ([OQ-32](10-decisions.md#oq-32-桁の単位) で確定) |
| 表示幅 / 表示列 | display width / column | 端末セル数。全角=2、結合文字=0 等。UAX #11 ベース。曖昧幅は設定で 1/2 |
| 幅危険書記素 | width-risky grapheme | 端末によって表示幅が食い違いやすい書記素 (絵文字の VS16・ZWJ 列・国旗・曖昧幅・PUA 等)。分類は eve-text、再出力戦略は 04 |
| char 近似モード | char approximation mode | 閾値を超える長大行を、書記素 = char・幅 = char ごとの表引き・折り返し OFF として扱うモード ([03 §11.5](03-core-design.md#115-長大行-nfr-106)) |
| 文字種の遷移 | character class transition | 単語移動の区切り規則。英数字 / 漢字 / ひらがな / カタカナ / 全角英数 / 記号 / 空白の分類が変わる位置で止まる (確定、OQ-117) |
| 改行の既定 | `default_eol` | 文書に新しく挿入する改行のコード。文書全体の改行コードではない (混在は `eol_stats`)。新規文書は全 OS で LF (確定 (ユーザー回答)、OQ-04) |
| 変更集合 | `ChangeSet` | 文書に対する挿入・削除の列 (Retain / Delete / Insert)。逆変換・合成・位置写像ができる |
| トランザクション | `Transaction` | ChangeSet + 適用前後の Selection + 由来 (Origin)。**文書変更の唯一の経路**。Undo 単位の最小構成要素 (連続入力などで複数が 1 つの Undo ノードに結合され得る) |
| 由来 | `Origin` | 変更を起こした主体。例: User / Command / Paste / Reload / Recovery / Ai / Plugin / External / Lsp。**列挙の正本は 03 §6.3** (本表は例示)。Undo/Redo は元の Origin + `is_undo` フラグ |
| 履歴ノード / 保存点 | `NodeId` / `history.saved` | Undo 履歴の各状態。保存した時点のノード ID を保存点とし、現在ノードと一致すれば「未変更」。v0.1 の履歴は線形で、NodeId は (世代, 位置) で表す (OQ-114 で確定) |
| 版 (文書の) | `Revision` | 文書の変更ごとに単調増加する番号。古いジョブ結果の破棄・写像の判定に使う (dirty 判定には使わない) |
| スナップショット | `Snapshot` | ある版の文書内容の不変コピー (rope の O(1) clone)。ジョブへ渡す |
| 不正バイトのエスケープ | PUA escape | デコードできないバイトを私用領域の 1 文字 (`U+10FF00..`) で保持し、保存時に元のバイトへ戻す方式 (03 §8.3。v0.1 は表示のみ、編集は v0.3) |
| 区分 B / 往復保持表 | roundtrip class B / `lossy_roundtrip` | 復号専用の文字 (EUC-JP の補助漢字、CP932 の重複符号化の非代表側) で、再エンコードすると元と別のバイト列になる箇所。v0.1 は件数と位置を検出して保存前に確認し、v0.3 で元のバイト列を保持する表 (`lossy_roundtrip`) を使ってバイト一致させる (ADR-0026) |
| 黙示置換 | silent substitution | エンコーダが表現不能文字をエラーにせず別の文字に写像すること (例: Shift_JIS の `¥`→0x5C)。保存時の encode→decode 照合で検出する |

**文書ヘッダの書式**: 各文書 (00〜12) の冒頭のヘッダ表は、少なくとも次の行をこの順に持つ。

- 文書固有の行 (v0.1 で読む節・関連など) はその後に置く。

### 7.1 文書運用ルール

1. **正の情報源**: 決定事項の状態は 10-decisions が正。状態の表記は「確定」「確定 (ユーザー回答)」「条件付き確定」(スパイクの結果を条件とする確定。10 では「条件付き確定 (S-nn)」と書く)「一部提案中」(方針などの一部が確定し、細目が提案中)「提案中」でとする (表記の定義は 10 §0.1)。他文書は ADR・OQ の番号で参照する。概念ごとの正本の所在は [README §4](README.md#4-正本マップ) に従う。正本でない文書は定義を **再掲せず参照** する。
2. **ID の不変性**: FR/NFR/ADR/OQ/AC と規範行 ID は一度振ったら再利用・振り直しをしない。廃止した ID は「廃止」と明記して残し、別の意味で再利用しない。本文では OQ を 10 の OQ 番号 (OQ-01〜) で参照する。10 の「残件 #n」と「v0.1 の範囲から外した項目 #n」は別の番号体系で、どちらも不変とする。
3. **矛盾発見時**: 文書間の矛盾は 10-decisions に OQ として起票し、解決後に両文書を更新する。
4. **責務境界**: どの概念をどの文書が決めるかは [README §4](README.md#4-正本マップ) に従う (文書と crate の対応は [02 §12.1](02-architecture.md#121-文書と-crate-の対応))。
5. **確定手続き**: PO が ADR・OQ を確認して状態を「確定」に変える。PO が確認する前の ADR・OQ を「確定」と書かない。ただし、裁量区分の OQ が期限までに異議なく推奨で確定する場合 ([10 §0.5](10-decisions.md#05-oq-の区分と回答の扱い)) を除く。実装着手の条件は [08 §5](08-roadmap.md#5-実装着手の条件-仕様確定のゲート)。
6. **PO 判断が要る変更の書き方**: 本文は推奨案で記述し、PO の判断が要る箇所に「(提案、OQ-<番号>)」を付ける。代替案は 10 の該当 OQ に置く。PO の回答が推奨と異なれば、本文を回答に合わせて書き換える。
7. **版の書き方**: フェーズ・時期は版名 (v0.1〜v1.0、v1.L、v1.X) で書く (08)。
8. **自己完結**: 仕様書の本文は docs/ の本編 (00〜12、README) だけで完結させる。作業用のメモやレビューの記録を参照しない。文書間の作業依頼の表 (「他文書への指摘」等) と、作業用の指摘番号 (レビューや依頼の行番号) を本文に残さない。未解決の論点は 10 の OQ として起票し、OQ 番号で参照する。改訂の経緯は本文に書かず、git で追う。
9. **用語集の書き方**: 用語集 (§6) の各行は定義 1 文と正本の節へのリンクだけにする。版・数値・手順・範囲の注記は書かず、正本の節に書く。
