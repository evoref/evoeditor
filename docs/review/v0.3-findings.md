# v0.3 の検討の指摘一覧 (2026-11-04)

v0.2.0 のリリースの直後に、v0.3 (整理・効率化・品質の版) の範囲を決めるため、コードと仕様を 3 つの視点 (安全性・正しさ / ロジックの効率・性能 / 構造・保守性と仕様との整合) で精査した。その指摘を、v0.3 のマイルストーン (M11〜M19) の作業の材料として残す。版の再編そのものは [08](../08-roadmap.md) と ADR に反映する (M11)。本書は作業の材料で、**正本ではない**。仕様と食い違うときは docs/00〜12 が正。

- 対象: `develop` の v0.2.0 (コミット `d84c453`) の時点のコード。行番号はこの時点のもの。分割の後は関数名で探す。
- 「確認」の列: **主** = 主のセッションが該当行を開いて確かめた。**報** = 精査した側が確かめたと報告し、主は未確認。**推** = 推測 (発生の条件や効果を実測していない)。着手の前に、報・推の行は該当行を開いて確かめる。
- 工数は 08 と同じ「週 (フルタイム換算、1 人 + AI 支援)」。v0.2 は見立て約 21 週が 8 暦日で終わったので、暦日はこれより短くなる見込み (根拠は 1 版分の実績だけ)。
- 振る舞いを変える修正は `fix/` の PR に分け、リファクタリング (`refactor`) の PR に混ぜない。

### 2.7 足す試験・fuzz・故障注入 (M13)

1. SAF-01: A の保存中に B へ切り替える・A を閉じる → A の保存の完了後も B の本文と履歴が変わらない。
2. SAF-02 / 02b: 不正バイトを含む文書を別の文字コードの別パスへ保存すると、何も書かれない。エスケープ文字を貼った文書も同じ。
3. SAF-03: 保存に失敗した dirty 文書と保存中に閉じた文書で、tick を進めてもスワップが残る。
4. SAF-04: 中止して終了の最中に MemFs が `ReplacedMovedToBackup` / `InPlaceFailed` を返すと、stderr にその行がある。kill テストに「取消し後の直接上書き中の kill」。
5. SAF-05: `FsyncFailed` / `ChangedAfterSave` がメッセージに出る。
6. SAF-07: panic する `InputOut` で `Fatal(InputThreadDied)` が届く。
7. SAF-12 / 13: proptest に複数 Edit の ChangeSet を足し、Undo / Redo の後も `eol_stats` と `long_lines` が数え直しと一致する。
8. **`fuzz_vt_input`** (新規): 任意のバイト列を任意の位置で入れる。overflow-checks を有効にする。
9. **`fuzz_encode`** (新規): 任意の文字列 × 6 文字コード × 3 方針で、panic なし・報告 0 件なら復号で一致・一括とチャンク分割で同じ出力・乾式走査と本番の一致。
10. **fuzz_editor の穴**: 引数付きのコマンド (`file.set_line_ending`・`edit.insert_text`) が一度も走っていない。長大行とジョブの経路に届かない (閾値を下げる設定を使う)。開き直し・再読込・外部変更・ジョブの交互の進行・マウスのドラッグが無い。
11. SAF-22 の回帰: JIS X 0212 だけの 1 MiB の 1 行の往復検査が 1 s 未満。
12. SAF-06 / 17: 開き直しと実行中の ReplaceAll の競合で、Revision が単調。
13. SAF-27: 読込の `try_reserve` の失敗を注入して、落ちずにメッセージを出す。
14. MemFs の故障注入: `metadata` だけ失敗 (SAF-20)、`rename` が EXDEV (SAF-23)、fsync の失敗 (SAF-05)。

## 3. ロジックの効率・性能 (PRF)

### 3.1 計測の前提 (報)

- `bm_103a --quick` (120×40、1 MB の日本語混在、ENV-W1): 折り返し OFF で `handle_input` p50 11 µs、入力から Frame の生成まで p50 299 µs。**core の区間の約 96% が Frame の生成**。折り返し ON で `handle_input` p50 107 µs、全体 p50 557 µs。
- v0.2.0 の BM-103b p50 1.57 ms の内訳は sent→render 1.20 ms。core は 0.28 ms なので、差の約 0.9 ms はスレッドの起床などで製品のコードの外 (推)。
- BM-103b-search (#334) p50 2.44 ms は不合格のまま例外で出荷した。
- 推移的依存 79 (Windows の normal、NFR-207 ≤ 90)。うち約 20 が ratatui 経由。

### 4.9 反対の論点 (構造)

- eve-core を複数の crate に割らない (ADR-0033 / OQ-126)。
- コマンド ID を enum にしない。仕様書の表から build.rs で生成しない (定数と突合の試験で足りる)。
- 設定を serde derive / proc-macro で作り直さない (位置付きの診断と「不正な項目だけ既定に戻す」挙動に合わない)。
- `write_atomic` を trait のフックの汎用手順に統合しない。win.rs と unix.rs を 1 つの trait に完全に統合しない。
- ディスク上の形式 (manifest・inflight・スワップの名前・一時ファイルの名前) と kill のフックの名前・位置を、整理のついでに動かさない。
- `#[non_exhaustive]` を struct に先に付けない (OQ-177 のとおり C3 から)。
- 既存の試験をシナリオ DSL に大量に移さない (Harness に寄せるほうが費用対効果が高い)。
- 3 つの VT パーサ (VirtualScreen / e2e の vt100 / accept_linux の tmux capture) を統合しない。xtask と cli.rs に clap を入れない。

M16 の作業の中で見つけたこと (範囲の外。後の版で扱う):

- **Windows の一時ファイルの `FlushFileBuffers` の失敗は、どれも警告のまま置換へ進む** (05 §4.2)。Unix は SAF-46 で `EIO`・`ENOSPC` 等を中断にしたので、OS の間で非対称。`ERROR_DISK_FULL`・I/O の誤りを中断にするかを決める (05 §4.2 を先に)。
- **起動時の提案に答えたときの `act()`** (`eve-core/src/io/leftover.rs`) は、表示した痕跡が無くなると、同じ T の記録のフラグをすべて消す。表示していない 2 件目の一時ファイルの記録も消える (前からの軽い点)。`scan` と同じく記録ごとに痕跡を見直す形にそろえる。
- **NFSv4 の idmap の失敗** で T が nobody に見えると、root の `fchown(nobody)` が成功して本当の所有者が nobody に変わり得る (前からの点。SAF-37 の対象外)。
- **非 root で、自分の uid のファイルでも一時ファイルの st_uid が T と違う** 場合 (NFS の all_squash 等) は、`AttrsNotPreserved` の警告だけで所有者が変わる (仕様も root に限っているので矛盾ではない)。
- **`TuiFrontend` を `entered` にならないまま drop すると**、「復元済み」の印は下りたまま出力の fd を閉じ、その後に緊急の復元が走ると閉じた fd に書き得る (前からの点)。
- **e2e の時間の検査**: ハードリンクの使えない作業の場所 (サブエージェントの worktree) では、既定の並列で時間の検査が数件落ちることがある (`--test-threads=2` なら通る。CI では通る)。
