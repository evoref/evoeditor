# v0.4 の計画の材料 (2026-11-11)

v0.3.0 のリリースの直後に、v0.4 (日本語と巨大ファイルの完成版) の着手の準備として、範囲の各項目について **仕様が実装に入れる詳しさか** を 3 つの領域 (文字コード / 巨大ファイル・長大行・検索 / 小さな独立機能と洗い出し) で点検した。その結果と、v0.4 のマイルストーン (M20〜M27) の案を、作業の材料として残す。版の範囲とマイルストーンの正本は [08 §2.5](../08-roadmap.md)、決定の正本は [10](../10-decisions.md)。本書は作業の材料で、**正本ではない**。仕様と食い違ったら仕様を採る。

- 対象: `develop` の v0.3.0 の後 (コミット `d48c31d`) の時点の仕様とコード。行番号はこの時点のもの。
- 「確認」の列: **主** = 主のセッションが該当の行を開いて確かめた。**報** = 点検した側が確かめたと報告し、主は未確認。**推** = 推測 (実測や試作をしていない)。着手の前に、報・推の行は該当の行を開いて確かめる。
- 工数は 08 と同じ「週 (フルタイム換算、1 人 + AI 支援)」。大きさの目安: S = 2 日まで、M = 1 週まで、L = 2〜3 週。v0.2 は見立て約 21 週が 8 暦日、v0.3 は約 33.5 週が約 7 暦日で終わったので、暦日はこれよりずっと短くなる見込み。暦日の下限は、技術検証 (S-04) と判定の夜間 fuzz の観測で決まる。
- v0.3 と同じく、振る舞いを変える修正は `fix/`、振る舞いを変えない整理は `refactor` の PR に分ける。機能は、**仕様の PR (`spec/`) を先に入れてから** 実装の PR (`feat/`) を出す (ADR-0001)。

### 1.3 人間 (PO) に尋ねる点として残すもの

次は推奨を決めきれない、または利用者に見える意味の決定なので、該当のマイルストーンの仕様の PR で選択肢として尋ねる。

| 論点 | いつ | 選択肢 |
|---|---|---|
| 保持方式で、編集して Undo で戻した範囲を「未編集」と扱うか | M22 の仕様 | 写像だけで判定 (戻しても代表バイト列になる) / 保存時に内容を照合して元のバイト列に戻す |
| 緊急退避・スワップから復旧した文書で、保持した元のバイト列を残すか | M22 の仕様 | 残す (manifest の形式を広げる。戻しにくい) / 残さない (復旧後は v0.3 と同じ確認に落ちる) |

| FR-110 で広げる文字コードの範囲と、公開する名前 | M26 の仕様 | encoding_rs の全部 / 数種に絞る |

### 5.3 追加ゲート (案。M20 で 08 §2.5 と 09 §8.2 に書く)

- (a) v0.3 のゲートの (a)・(c)・(d)・(f) を続ける (試験とゴールデン、clippy と `missing_docs`、仕様の検査、`CONTRACT_VERSION` は 0)。
- (b) 往復コーパスのバイト一致: 区分 A / B は **編集した後に元の文字コードで保存して**、編集していない範囲がバイト一致する。区分 D (ISO-2022-JP) は編集していない行がバイト一致する。不正バイトを含む ISO-2022-JP は対象から除く (ENC-07)。
- (c) 基準機の BM が v0.3.0 の記録から劣化しない。NFR-106 の 50 ms と、先行表示の 300 ms (Shift_JIS の 100 MB を含む) を満たす。

### 5.4 反対の論点

- **保持方式は効果に比べて重い**: 重複符号化の非代表側や補助漢字を含む文書は多くない (推)。行の単位で保持して確認 (E2') を残す縮小案がある。→ NFR-303 は Must で、v0.4 の主題の中心なので、仕様どおり範囲の単位で入れる。保持の単位は M22 の仕様で、実装の重さを見て決め直してよい。
- **Partial は速い機械では効果が見えない** (BIG-03)。遷移が増えて壊れやすい。→ FR-122 は Must なので送らず、最小の形にする (§1.2)。遅い機械・遅いディスクと Shift_JIS では効果がある。
- **複数行の正規表現が最大の項目**。→ S-04 を最初 (M21) に置き、結果が悪ければ 08 §3 の退路で範囲を縮める。
- **ユーザーの言語ファイルは需要が見えない** (ja と en は同梱済み)。公開のファイル形式を固定する。→ 10 の推奨どおり v0.4 に置くが、M26 の仕様の時点で PO が送る判断をしてもよい。
- **工数の見立ては過大の見込み**: v0.2 と v0.3 の実績では、暦日は見立ての 1/20 以下だった。ただし v0.4 は機能の追加で、v0.3 (整理) より仕様の決定と人の確認 (PO への問い、§1.3) が多い。
