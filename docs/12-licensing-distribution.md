## 3. ライセンスと公開の範囲

### 3.1 配布物

| 配布物 | 中身 | ソース | 版 |
|---|---|---|---|
| TUI 版 (`evoeditor`) | core・TUI・ヘッドレス (駆動 API は OQ-120)・v1.L 以降の LSP / AI | 公開・OSS、Apache-2.0 単独 (確定、OQ-152 / 19) | v0.1〜 |
| 公開 crate (`eve-*`) | TUI 版を構成する lib crate。外部の消費者 (駆動 API のクライアント等) も使える | 同上 | 公開の時期は 1.0 の前 (OQ-20、確定 (ユーザー回答)、§4.2) |

### 3.2 本体のライセンス (OQ-19)

**決定 (確定 (ユーザー回答))**: 公開リポジトリ (TUI・core・ヘッドレス等) のライセンスは **Apache-2.0 単独**。リポジトリに既にある `LICENSE` (Apache-2.0) と一致する。Rust の crate の多くは Apache-2.0 を含むライセンスで、相互に使える。特許条項と NOTICE の含意は下の「Apache-2.0 を採ることの含意」。

- **理由**: (1) 特許の明示的な許諾と特許報復の条項を持つ (下記)。(2) 公開 crate (例: `eve-text` / `eve-encoding`) を他のプロジェクトが使える。(3) 外部寄稿を DCO で受ける (§3.5、OQ-154 は確定 (ユーザー回答))。
- **ライセンスの変更**: DCO で外部寄稿を受けた後に Apache-2.0 から別のライセンスへ変えるには、寄稿者全員の同意が要る (§3.5)。細目は弁護士確認の対象。
- **LICENSE ファイルと表記**: リポジトリ直下の既存の `LICENSE` (Apache-2.0 の全文) をそのまま使い、`NOTICE` を追加する (下記。最初の push の前の M0e に作り (PC-4)、v0.1 のアーカイブに同梱する、[08 §4](08-roadmap.md#4-マイルストーン)・[08 §2.2](08-roadmap.md#22-v01-最小核))。各 crate の `Cargo.toml` は `license = "Apache-2.0"` (ワークスペースの `[workspace.package]` で一括して指定し、各 crate は `license.workspace = true`)。ソースファイルごとの SPDX ヘッダ (`// SPDX-License-Identifier: Apache-2.0`) は任意 (付けるかは 11 の規約で決める)。
- **cargo-deny の自社 crate の表記**: 公開リポジトリの自社 crate (`eve-*`、`xtask` を含む) はすべて `license = "Apache-2.0"` を持ち、`deny.toml` の許可リスト (05 §17.1) の `Apache-2.0` で通る。公開しない補助 crate (`publish = false`) も同じ表記にする (表記の無い crate を作らない)。

#### Apache-2.0 を採ることの含意

法的助言ではない。下記は条文の一般的な読みに基づく設計上の整理で、§3.8 の期限で弁護士の確認を受ける (LP-4)。

| 論点 | Apache-2.0 の規定 (概要) | 影響 | 対応 (提案) |
|---|---|---|---|
| 再利用と再配布 | 誰でも複製・改変・再配布・サブライセンスでき、派生物のソースの公開義務はない (第 2 条) | 公開 crate を他のプロジェクト・製品が自由に使える | 受け入れる (Apache-2.0 を採る目的の 1 つ)。core に特定の frontend 向けの分岐を入れない (LP-2) |
| 特許の許諾 | 寄稿者 (権利者自身を含む) は、自分の寄稿に必然的に含まれる自己の特許請求項について、利用者に無償の特許ライセンスを与える (第 3 条) | 公開リポジトリに入れた発明は利用者に許諾済みになる。外部の寄稿者の特許も同様に許諾されるので、寄稿を取り込む際の特許リスクは下がる | 特になし |
| 特許報復 | 公開リポジトリのコード (またはその寄稿) が特許を侵害すると主張して訴訟を起こした者は、その著作物について受けた特許ライセンスを失う (第 3 条) | 利用者が本プロジェクトに関する特許訴訟を起こしにくくなる (防御的な効果) | 特になし |
| 帰属表示と NOTICE | 再配布するときは、ライセンス文の写しを渡し、改変したファイルに改変した旨を表示し、ソースの著作権・特許・商標・帰属の表示を残し、`NOTICE` ファイルがあればその帰属表示を配布物 (同梱の NOTICE、文書、または表示画面のいずれか) に含める (第 4 条) | 再配布者 (派生物を含む) に帰属表示の義務がある。本プロジェクトの配布物にも `LICENSE` と `NOTICE` を同梱する (§5.4) | 公開リポジトリに短い `NOTICE` (製品名・著作権者・Apache-2.0 で提供される旨) を置く。`NOTICE` は再配布者が削れない帰属表示になるので、広告的な文言や頻繁に変わる内容を書かない。寄稿者による `NOTICE` への追記は原則受け付けない方針を `CONTRIBUTING.md` に書く。`THIRD-PARTY-NOTICES` (§3.6) とは別のファイルにする |
| 寄稿の条件 | 寄稿者が別段の明示をしない限り、意図的に提出した寄稿はこのライセンスの条件で提供されたものとみなす (第 5 条) | inbound = outbound が条文で裏付けられる | `CONTRIBUTING.md` に「寄稿は Apache-2.0 で提供される」と明記する。寄稿の権利の表明は DCO (§3.5、OQ-154、確定 (ユーザー回答)) |
| 商標 | ライセンスは商標の使用を許諾しない (第 6 条。NOTICE の再現に必要な範囲を除く) | 第三者はコードを使えても、名称・ロゴを使ってよいことにはならない | 名称・ロゴの使用方針は §3.7 (OQ-01) |
| 無保証・責任の制限 | 「現状のまま」提供し、保証・責任を負わない (第 7・8 条) | — | `LICENSE` のとおり |
| 他ライセンスとの両立 | GPL-3.0 のプロジェクトは Apache-2.0 のコードを取り込めるが、GPL-2.0 のみのプロジェクトとは両立しないとされる | GPL-2.0 のみのプロジェクトは公開 crate を使えない | 受け入れる (影響は小さい見込み) |

### 3.3 OSS として公開する範囲 (OQ-152)

**決定 (確定 (ユーザー回答))**: TUI と core を含む公開リポジトリ全体を **OSS (Apache-2.0 単独)** で公開する。公開リポジトリに置くもの: core・TUI・ヘッドレス (testkit・参照レンダラ・駆動 API)・`xtask`・仕様書 (`docs/`)。

- TUI と core を OSS (Apache-2.0 単独) で公開する。利用者と寄稿者を得やすく、仕様書・駆動 API・シナリオ DSL を公開して AI エージェントとの開発構成 (ADR-0033) を外部とも共有できる。公開 API の互換を守る責務が増える (§4)。
- **派生物 (非公開・商用を含む) との関係** (確定 (ユーザー回答)、2026-10-20): ライセンスは **現行どおり Apache-2.0 単独 + DCO** で決定した (copyleft や二重ライセンスは採らない)。Apache-2.0 は派生物のソースの公開義務を課さないので、外部の寄稿を含む公開リポジトリのコードを、非公開の製品 (商用を含む) に組み込める。条件はライセンス文の写しの同梱、著作権・帰属の表示と `NOTICE` の保持、改変したファイルへの改変の表示 (第 4 条、§3.2)。そうした派生物の配布物にも `LICENSE`・`NOTICE`・`THIRD-PARTY-NOTICES` を同梱する。名称・ロゴの使い分けは §3.7 (OQ-01) の使用方針で扱う。将来 Apache-2.0 以外へ変える余地を残したい場合は、外部寄稿の受付開始 (OQ-174) の前に CLA へ切り替えるかを決める (§3.5)。

### 3.4 AI 機能の扱い

- AI 連携 (ローカル LLM・クラウド) は core の機能に当たり、TUI とヘッドレス (駆動 API) から同じに使える (LP-1。eve-ai は公開リポジトリの crate)。資格情報は利用者自身のもの (ローカルサーバ、または利用者の API キー) で、エディタは AI の中継サーバを持たない (P2・ADR-0019・NFR-509 / 510 のオフライン完結と整合)。06 の設計 (eve-ai は core と `AiService` で接続) を変えない。

### 3.5 寄稿ポリシー (OQ-154)

- **寄稿の受け方 (CP-1、確定)**: **DCO** (Developer Certificate of Origin。コミットに `Signed-off-by:` を付け、寄稿者が寄稿する権利を持つことを表明) + inbound = outbound (寄稿は Apache-2.0 で受ける)。寄稿者の負担が小さい。将来、Apache-2.0 から別のライセンスへ変えるには寄稿者全員の同意が要る (下の「DCO の意味と限界」)。

- **用語**: **DCO** は、寄稿者がコミットごとに `Signed-off-by: 氏名 <メール>` の 1 行を付け (`git commit -s`)、「この変更を自分が書いた、または提出する権利があり、プロジェクトのライセンスで提供する」と宣言する仕組み (Linux カーネル等が採用)。署名の書類や事前の登録は要らない。**CLA** (Contributor License Agreement) は、寄稿者がプロジェクトの権利者と結ぶ契約で、寄稿物を別のライセンスで配布する権利 (再ライセンス) などを権利者に与える。寄稿の前に署名が要り、その記録 (bot 等) を管理する。**inbound = outbound** は「寄稿を受けるライセンス」と「プロジェクトを配布するライセンス」を同じにすること。
- **決定 (確定 (ユーザー回答))**: **DCO を既定** とする。CLA は、将来再ライセンスが必要になった場合にだけ導入を検討する。Apache-2.0 第 5 条により寄稿は Apache-2.0 で提供されたものとみなされ、DCO はそれに「寄稿する権利があること」の表明を加える。`CONTRIBUTING.md` は最初の push の前に最小の版 (外部からの PR をまだ受け付けていない旨・DCO の手順・寄稿のライセンス。§5.6 の PC-4) を置き、外部寄稿の受付開始前に完全な版にする。CI の DCO チェックは最初の CI (08 §2.2 の M1 のタスク (0)) から入れる (11 §9.4)。外部寄稿の受付開始前に来た PR の扱いは [OQ-171](10-decisions.md#28-oq-161-以降-仕上げ段階の追加起票)。受付開始の条件は 08 §4 (提案、OQ-174)。
- AI コーディング支援で生成したコードの扱い (権利・表示) は、寄稿ポリシーの文書 (`CONTRIBUTING.md`) に方針を書く (内容は **要確認**、弁護士確認の対象)。方針の文案を決める時期は v0.1 のリリース後、弁護士の確認は外部寄稿の受付開始前 (§3.8 の LR-3、[OQ-164](10-decisions.md#28-oq-161-以降-仕上げ段階の追加起票)。同じ OQ でアンインストール手順・`SECURITY.md`・minisign 公開鍵の公開場所も扱う)。

#### DCO の意味と限界

本節は法的助言ではない。条文の一般的な読みに基づく設計上の整理であり、§3.8 の期限で弁護士の確認を受ける (LP-4)。

| 論点 | 整理 |
|---|---|
| 商用利用と派生物 | Apache-2.0 は商用利用と派生物の配布を許す (第 2 条)。条件は、ライセンス文の写しの同梱、著作権・帰属の表示と `NOTICE` の保持、改変したファイルへの改変の表示など (第 4 条、§3.2 の含意の表) に限られ、ソースの公開義務はない |
| DCO の意味 | 寄稿者が「その変更を提出する権利を持ち、プロジェクトのライセンス (Apache-2.0) で提供する」と宣言するもの。利用を妨げる条件を加えない |
| DCO でできないこと | 寄稿者の著作権は寄稿者に残る。そのため **後から Apache-2.0 以外のライセンスへ変更することは、寄稿者全員の同意なしにはできない**。変更が必要になった時点で、CLA の導入 (以後の寄稿) と、同意の得られない既存の寄稿の書換え (除去と再実装) で対応する |
| 商標 | 名称・ロゴは Apache-2.0 で許諾されない (第 6 条)。使用方針は §3.7 ([OQ-01](10-decisions.md#oq-01-正式名称とバイナリ名)) |

### 3.6 依存・同梱物のライセンス方針 (公開リポジトリの依存とアセットのライセンス、ADR-0018)

本節の方針は **確定 (ユーザー回答、2026-10-20)** (ADR-0018 の依存方針の部分も確定)。**公開リポジトリの層の許可リストの正本は [05 §17.1](05-platform.md#171-ライセンス運用-adr-0018-の具体化検査は-09)** で、本書は再掲しない (M1 のタスク 0 の `deny.toml` は 05 §17.1 の許可リストで作る。`NCSA` は `fuzz/` 側のみ、08 §5、ADR-0018)。

| 層 | 対象 | 許可 | 不可 | 検査 |
|---|---|---|---|---|
| **公開リポジトリ** (TUI 版と公開 crate) | 公開リポジトリの依存 | 05 §17.1 の許可リスト (許容的ライセンス。MPL-2.0 などは個別承認) | GPL / AGPL / LGPL (静的リンク)、非 OSI (ロイヤリティフリー条項等) | cargo-deny (公開リポジトリの CI) |

- **同梱アセット**: tree-sitter 文法とハイライトクエリ (ADR-0018 のとおり MIT / Apache 由来のみ)、テーマ。すべて `THIRD-PARTY-NOTICES.md` に列挙する。依存の帰属表示は、公開リポジトリでは v0.1 から cargo-about で `THIRD-PARTY-NOTICES.md` を生成してリリースに同梱する (05 §17.1)。
- **資産台帳** (提案): 同梱アセット (文法・クエリ・テーマ) は `assets/NOTICES.toml` に 1 件 1 行 (出所 URL・版・ライセンス・帰属表示の要否) で記録し、`xtask check-assets` (**v0.2 から**。最初の同梱資産と同時に入れる。v0.1 は同梱資産 (文法・クエリ・テーマのファイル) が無いので置かない) が「台帳に無いファイルの同梱」「許可リスト外のライセンス」「帰属表示の欠落」を CI で検出する。`THIRD-PARTY-NOTICES` は台帳と依存の帰属表示から生成する。tree-sitter のハイライトクエリは文法と別に出自を記録する (流用元が MPL-2.0 等のことがある、05 §17.1)。
- **再配布の可否**: 依存のライセンスが再配布 (商用の再配布を含む) を許すこと (許容的ライセンスは許す) を、許可リストの条件にする。

### 3.7 名称と商標 (OQ-01)

## 4. 公開 API の安定性 (外部の消費者)

公開 crate は TUI 以外の **外部の消費者** にも使われ得る: 駆動 API のクライアント、第三者のプロジェクト。外部の消費者が公開 crate を使う可能性があるので、境界型は契約版で管理する (02 §8.4)。

### 4.1 外部の消費者が依存してよい範囲

| crate | 依存してよい要素 | 根拠 |
|---|---|---|
| `eve-host` | `Frontend` trait、`Host` (`run` / `step`)、`HostMsg` の公開部分 | 02 §9.2 |
| `eve-view` | 境界型すべて (`InputEvent` / `Frame` / `Effect` / `Capabilities` / `EditorEvent` / `Proposal` / `Query` 等)、`CONTRACT_VERSION` | 02 §8.4 |
| `eve-config` | 解決済み設定の型 | 07 §5 |
| `eve-core` | **公開ファサード (`Editor`) のみ** (02 §4.1 の規則と同じ)。内部モジュールには依存しない | 02 §4.1 |
| `eve-testkit` | テスト部品 (`HeadlessFrontend` / `CellOccupancy` / `Harness` (シナリオランナー) / 偽 Port (`MemFs` / `ManualClock` / `ManualJobSpawner`))。外部の消費者のテスト (dev 依存) から、**版を固定して** (`=0.y.z` または git のタグ、§4.2) 使う。公開 crate として publish する (公開の時期は他の公開 crate と同じ OQ-20) | 09 §3.4、11 §9.5 XC-6 |

`eve-platform` は `eve-host` の normal 依存なので crates.io には一緒に publish する (09 §9.2 の手順 11) が、上の表に含めず、外部の消費者が直接依存してよい範囲の外 (互換を約束しない内部用の crate) とする (02 §4.1 の注。提案、OQ-20)。

### 4.2 互換の規則

| 規則 | 内容 |
|---|---|
| 契約版 | 境界型の互換の単位は `CONTRACT_VERSION` (02 §8.4)。C3 (契約版 1。v0.1 のリリースゲートにはしない、ADR-0039) 以降、破壊的変更は契約版 2 として **直近 2 版を受理する並行期間** を置く。外部の消費者があるときの並行期間は、公開側のリリース 2 回分以上 (確定、OQ-157) |
| crate の版 | 公開 crate は semver に従う。1.0 (v1.0 のリリース) までは 0.x で、マイナーの上げで破壊的変更があり得る。ただし §4.1 の範囲は C2 以降「追加のみ」(02 §8.4) |
| 公開の方法 | crates.io への公開の時期は OQ-20 (10 の残件 #1。確定 (ユーザー回答、2026-10-20))。(A) を採る: v0.1 は `cargo install --locked --git <repo> --tag v0.1.0 evoeditor` に限り、bin `evoeditor` と依存する公開 crate を crates.io に出すのは 1.0 の前。出した時点から 0.x の間、§4.1 の範囲以外の公開 API は「安定性の保証なし」と crate の文書に明記する (`eve-core` の内部モジュールは `pub(crate)` か `#[doc(hidden)]`)。外部の消費者は公開 crate を **正確な版 (`=0.y.z`) または git のタグ** で固定して依存し、上げるときに追従する (確定、OQ-157。crates.io に出すまでは git のタグ)。名前の空きは v0.1 のリリース前と各リリースの前に照会して監視し、先に取られた場合は接頭辞を変えず、(i) その crate を公開せず git のタグで消費するか、(ii) 公開名だけを変える (`[package] name` を変え、`[lib] name` でコード上の名前を保つ)。名前の空き (2026-10-16): `evoeditor` と `eve-*` はすべて未登録 (§3.7) |
| 互換の破れの検出 | 公開リポジトリの Frame JSON ゴールデン (契約テスト) と、ヘッドレス参照レンダラの parity (02 §8.4)。v0.1 は `HeadlessFrontend` と ASCII の Frame のスナップショットまで。外部の消費者の側は §4.3 の下流 CI |
| 境界型の不足 | 外部の消費者の利用で見つかった境界型の不足は、公開リポジトリに契約変更要求として起票し、C2 / C3 で許される「追加」で入れる。1 つの消費者の都合だけで公開 API に破壊的変更を入れない |

### 4.3 下流 CI

- 公開側の契約変更要求には、ヘッドレス参照レンダラと TUI の更新を同じ PR に含める (02 §8.4)。外部の消費者は契約版の並行期間内に追従する。
- **契約テストの受け渡し** (提案): 公開側の CI に `contract-export` ジョブを置き (v0.1 には置かない、ADR-0039)、このジョブが契約テストの成果物 (Frame JSON ゴールデン・シナリオ・`CONTRACT_VERSION`) を公開 crate / リリースに添付し、外部の消費者はそれを取り込んで同じシナリオを回す。
- **テスト部品の共有**: `eve-testkit` (`HeadlessFrontend` / `CellOccupancy` / シナリオランナー) は公開 crate として publish し、外部の消費者は版を固定して使う (§4.1)。`xtask` の関数も同じ crate (または公開 crate) から使い、外部のリポジトリに複製しない (11 §9.5)。

## 5. 配布と更新

### 5.1 配布経路 (TUI)

- TUI 版の配布は [05 §18](05-platform.md#18-配布-パッケージ署名公証) のとおり: **v0.1 は Windows x86_64 のみ** で、GitHub Releases (Windows x86_64 の zip (`THIRD-PARTY-NOTICES` 等を同梱、§5.4) + `SHA256SUMS` + minisign 署名) と `cargo install --locked --git <repo> --tag v0.1.0 evoeditor` (確定 (ユーザー回答)、[ADR-0042](10-decisions.md#adr-0042-v01-の最小核-案-lwindows-のみの出荷日本語のみの-ui))。macOS / Linux のアーカイブ (Linux の musl 静的版を含む) と macOS の署名・公証は、macOS / Linux を出荷する v0.2 (確定 (ユーザー回答)、OQ-15。macOS は ad-hoc 署名で出し、Developer ID と公証の適用は OQ-76) から。Windows aarch64 のアーカイブは v0.2 以降。v0.4 で各パッケージマネージャ (Homebrew / Scoop / winget / AUR / apt 等。macOS / Linux 向けはその OS を出荷していることが前提) と `cargo binstall`。crates.io への公開の時期は OQ-20 (10 の残件 #1。確定 (ユーザー回答): 1.0 の前。§4.2)。
- **対象 OS と動作確認の状況**: v0.1 の対象は Windows 11 の Windows Terminal と conhost (確定 (ユーザー回答)、OQ-15。Windows 10 は検証環境が無いので v0.2 以降の候補)。開発環境は Windows のみで、Windows は開発機で動作確認する。macOS / Linux は **v0.1 では出荷しない** (実機で確かめられない OS を出荷しない、ADR-0042)。core 系 crate は OS に依存しないまま保ち、CI の Linux で Linux CI の対象 crate (core 系 + `eve-host` + `eve-testkit`、09 §6.4) のビルドとヘッドレスのテストを行う (配布物は作らない)。既知の制約の正本は [01 §4.6](01-requirements.md#46-v01-の既知の制約-リリースノートとヘルプに明記する) で、リリースノートと README にも載せる。

### 5.2 署名と検証

- TUI のリリースは minisign で `SHA256SUMS` に署名し、公開鍵をリポジトリの `README.md` とリポジトリ直下の `minisign.pub` (と、リポジトリの外の経路) に置く ([05 §18.9](05-platform.md#189-minisign-署名の検証-提案oq-164))。minisign の秘密鍵は CI に置かず、メンテナの手元で署名する (11 §9.7)。
- OS のコード署名 (Windows の Authenticode、macOS の Developer ID 署名 + 公証) は 05 §18.3 / §18.4 (OQ-75 / 76)。v0.1 の Windows の zip はコード署名なし (minisign のみ。Windows の署名は v0.4、OQ-75)。macOS は v0.2 から ad-hoc 署名で出し、Developer ID 署名と公証の取得時期と適用は未決 (OQ-76、05 §18.4)。Windows の署名の第一候補は SignPath Foundation (Azure Artifact Signing は個人では米国・カナダの在住者に限られる)。
- コード署名の資格情報は CI の保護された秘密情報にだけ置く (11 §9.7)。

### 5.3 更新

**確定 (ユーザー回答)**: **エディタ内に更新機能を持たない** ([ADR-0040](10-decisions.md#adr-0040-更新の方針-エディタ内に更新機能を持たない))。TUI は配布経路ごとの手段で更新し、自動更新を実装しない (U1)。

### 5.6 公開前チェック (最初の push の前、OQ-160 / 168)

公開リポジトリは **public のまま開発し、docs/ も最初の push から公開する** (確定 (ユーザー回答)、[OQ-168](10-decisions.md#oq-168-開発期間中のリポジトリの公開状態))。push した内容は **全ブランチの履歴 (コミットメッセージ・著者情報を含む) とともに直ちに公開され**、後から履歴を消しても複製やキャッシュに残り得る。そこで、**最初の push ([08 §4](08-roadmap.md#4-マイルストーン) の M0e) の前に**、公開範囲 (OQ-160 は確定 (ユーザー回答、2026-10-20): 全文書を公開) に沿って、次の 7 項目を **作業ツリーと push する履歴の全体に対して** 行う (**PC-1〜PC-7 は 2026-10-20 に実施済み**。下の表は将来の参照と、以後の push の前の見直しのために残す)。最初の push の後は、PC-1・PC-2・PC-6 の対象が入っていないことを各 push の前に確かめ (11 §9.7)、CI と GitHub の秘密検出 ([OQ-169](10-decisions.md#28-oq-161-以降-仕上げ段階の追加起票)) で補う。PC-3〜PC-5・PC-7 は内容を変えるたびに見直す。結果はメンテナの手元の記録に残す (リポジトリには書かない)。

| # | 項目 | 内容 |
|---|---|---|
| PC-1 | 基準機の情報の一般化 | docs に機種名・CPU や SSD の型番・容量・OS のビルド番号・ウイルス対策ソフトの製品名・ドライブ文字を書いていないことを確かめる。基準機は環境 ID (例 `ENV-W1`) と一般化した構成だけで記す (01 §3.0)。詳細はリポジトリの外の非公開のメモに置く (11 §9.7)。docs は一般化済みで、最初の push の前にもう一度確かめる。一般化する前の内容をコミットしない (手元の履歴に残っても push で公開される) |
| PC-2 | 再 grep | 作業ツリーと履歴 (全ブランチの全コミットの内容とコミットメッセージ) を、メールアドレス・ユーザー名を含むパス (`C:\Users\…`)・ドライブ文字で始まる絶対パス・個人名・`sk-`・`ghp_`・秘密鍵の形 (`-----BEGIN` で始まるブロック) と minisign の鍵の形 (`untrusted comment:` で始まる鍵ファイル) で検索し、該当を除く (手元の履歴にあれば push の前に履歴を書き換える。push した後に秘密情報が見つかったら、まず鍵・トークンを失効させる (11 §9.7))。基準機の型番・製品名の語も同時に検索する。製品名・型番の語は **単語境界で** 検索する (`rg -w` 等。ロケール用語の `CODESET` のような語への部分一致を誤検出しない)。検索語の一覧はリポジトリの外の非公開のメモに置く (11 §9.7)。あわせて、時点を示す表記 (「2026-10 時点」等) が push の時点で古くなっていないかを確かめる |
| PC-3 | README の状態 | リポジトリ直下の `README.md` (`develop` のもの。v0.1.0 のリリースまでは既定ブランチ (OQ-170) で訪問者が最初に見る) に、(1) 開発中で v0.1 は未リリースであること、(2) 仕様書 (docs/) を作業中の版として公開していること (v0.1.0 のリリース以後は「公開した仕様」は `main` の docs/ (リリースした版に対応) で、`develop` の docs/ は作業中の版であること)、(3) ブランチの役割 (`main` はリリースした版、開発は `develop`。11 §9.1)、(4) 外部からの PR はまだ受け付けていないこと (Issues での報告・意見は受ける。扱いは OQ-171)、(5) ライセンス (Apache-2.0) を書く。`docs/README.md` (仕様書の索引) の「ステータス」がリポジトリの実態と一致していることも確かめる |
| PC-4 | `NOTICE`・`SECURITY.md`・`CONTRIBUTING.md` | リポジトリ直下に置く (08 §4 の M0e)。最初の push には鍵の公開部分 (`minisign.pub`・`.github/allowed_signers`・`.github/fuzz-recipients.txt`) も置く (08 §4 の M0e、PC-6 (3))。`NOTICE` は §3.2 の方針 (製品名・著作権者・Apache-2.0 で提供される旨の短い文) どおり。`SECURITY.md` は最小の版 (報告の窓口 = GitHub の private vulnerability reporting、開示の方針と対応の目安の日数、v0.1 は未リリースで配布物が無いこと。書く内容と運用の手順は 11 §9.8。更新方法の案内は v0.1 のリリース前に加える、§5.5)。`CONTRIBUTING.md` は最小の版 (外部からの PR をまだ受け付けていないこと (受付の開始は §3.5 と §3.8 の LR-2 / LR-3 の後)、DCO の手順 (`git commit -s`。メンテナとエージェントのコミットも同じ)、寄稿は Apache-2.0 で提供される旨、`NOTICE` への追記を受け付けない方針、Issue の出し方)。完全な版 (09 §11.4) は外部寄稿の受付開始前 |
| PC-5 | GitHub の設定 | (1) Issues は有効 (テンプレート付き、PC-7)。(2) Pull requests は外部から受けない (PC-3。制限の方法は **要確認** で、扱いは OQ-171)。(3) Discussions と Wiki は使わない。(4) GitHub Actions は有効にする (public のリポジトリでは標準のランナーが無料)。ワークフローは M1 のタスク (0) から置く (08 §2.2)。最初の push の前に、`GITHUB_TOKEN` の既定の権限を読み取りにし、外部の寄稿者 (fork) からの PR のワークフローの実行に承認を要する設定にする (11 §9.7)。v0.1 の間は CI にシークレットを置かない (リリースの署名は手元の minisign だけ、§5.2)。(5) secret scanning と push protection を有効にする (OQ-169。利用できる範囲は **要確認**)。(6) 既定ブランチは OQ-170。(7) push の直後に、`main`・`develop` のブランチ保護 (直接 push・force push・削除の禁止、PR 必須、管理者のバイパスなし。単独開発の期間は承認必須を 0 にし、必須のステータスチェックで merge を止める。必須の CI は M1 のタスク (0) で CI を置いたときに加え、チェックの名前は固定する) と、タグ `v*` の保護 (作成と削除をメンテナに限る) を設定する (設定の内容は 11 §9.1)。(8) Dependabot (`.github/dependabot.yml`、週 1・グループ化、09 §6.3) と Dependabot alerts を有効にする |
| PC-6 | 公開される付随情報とテストデータ | (1) コミットの著者情報 (氏名・メールアドレス) が公開されてよい形 (意図した名前と、公開してよいアドレス。アドレスを出したくなければ GitHub の noreply アドレス) であることを、push する全コミットについて確かめる。(2) **テストデータの規則** (確定 (ユーザー回答)): コーパス・テスト用のファイルは合成データか、再配布が許されるデータ (出典とライセンスを記録) だけを使い、実際の個人の文書を使わない (09 §4)。(3) **fuzz の成果物** (確定 (ユーザー回答)): 公開リポジトリの Actions のログと artifact は第三者が取得できるので、クラッシュ入力は **メンテナの公開鍵 (`age`) で暗号化した artifact** としてだけ上げ、ログには入力もスタックも出さない (`-close_fd_mask=3`)。受取人の公開鍵はリポジトリの `.github/fuzz-recipients.txt` に置き、秘密鍵はメンテナの手元だけに置く (復号はメンテナのみ)。再現はメンテナが復号して手元で行う (09 §6.3、11 §9.7)。最初の push の前に `.github/fuzz-recipients.txt` に秘密鍵が混ざっていない (公開鍵だけである) ことを確かめる |
| PC-7 | 利用者の報告窓口 | 最初の push の前に、Issues (バグ報告・機能要望・端末互換のテンプレート付き、09 §11.4)・`SECURITY.md`・GitHub の private vulnerability reporting を有効にする (§5.5、OQ-164)。v0.1 のリリースの前に、パニック時の文言が案内する Issue の URL (04 §14.4) がこの窓口を指すことと、`SECURITY.md` に更新方法の案内があることを確かめる (09 §8.2) |
