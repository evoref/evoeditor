## 所見

1. **BM-102a (起動 (a)、1 MB のファイルあり) は v0.3.0 より約 1.3 ms (+25%) 遅い (本当の劣化)**。同じ速い状態で交互に 3 ラウンド測っても、rc.1 は 6.30〜6.96 ms、v0.3.0 は 4.98〜5.45 ms で重ならない。目標 (p50 25 / p99 50 ms) に対しては十分な余裕があり、合否には効かない。BM-101a (ファイルなし) の増分は約 0.2 ms (+7%) なので、約 1.1 ms はファイルを開く起動に固有の分。一方、ヘッドレスの読込ジョブだけを測る BM-104-1m (同じ 1 MB 級の読込) は差が無いので、読込のジョブ (復号・区分 B の記録の収集・木の構築) の費用ではない。
   - **原因 (切り分けた)**: 同梱の言語の表 (`locales/ja.toml`) の TOML の解析 (`Catalog::parse`。速い状態で約 1.33 ms) の場所が変わったこと。v0.3.0 はこの解析を最初の Frame の生成で遅れて行っていて、その間は io スレッドで読込のジョブがもう走っていたので、時間が本文の Frame までの区間に出なかった。#558 (fe350a5、M26 の (2)) から、起動の設定読込の段 (`bins/evoeditor/src/settings.rs` の `setup_locale` の `Catalog::builtin_shared`) で解析するようになり、この段は読込のジョブの投入 (`open_initial_files`) より前にあるので、解析の時間がそのまま乗る。
   - **切り分けの計測**: v0.3.0・5d03a1c (#558 の前)・fe350a5 (#558)・90b2c81 を `git archive` で写し、起動の経路に一時的な印を足して、`bm_pty --only 102 --runs 300` を同じ時間帯に交互に 3 ラウンド回した。BM-102a の p50 は v0.3.0 が 4.87〜5.34 ms、5d03a1c が 4.91〜5.33 ms、fe350a5 が 6.22〜6.39 ms、rc.1 が 6.19〜6.57 ms で、段差は #558 の 1 か所だけ。内訳では「main → 読込のジョブの開始」が +1.36〜1.42 ms (うち `setup_locale` が 0.09 → 1.46 ms、その中の 1 回目の `Catalog::builtin_shared` が 1.33 ms)、最初の Frame の生成が 1.30〜1.34 → 0.13 ms (解析が済んでいるため)。
   - **仕様との関係**: 解析を設定読込の段に置くこと自体は仕様どおり (02 §9.5 の手順 2 は設定読込の予算に「同梱の言語ファイルの読込を含む」と書く。07 §17.4 は表を `Arc` で持つ)。ただし 07 §17.1 の「サイズと起動時間」は、同梱の表のデシリアライズの目安を 1 ms 以下とし、超えるならビルド時に静的な表 (キー → 文字列の配列) に変換して埋め込む方式に切り替えるとしている。v0.3.0 でも約 1.2 ms でもう目安を超えていた (遅れて作るので隠れていた)。
   - **BM-101a の +0.2 ms**: 同梱の `ja.toml` が 48.6 KB / 647 キーから 66.3 KB / 827 キーに増えた分の解析の増分と見る (印での推定)。
   - **扱いの案**: 目標 (NFR-102) の合否には効かないので、rc.1 の判定はこの所見を書いて通す。直し方は 07 §17.1 のとおりの静的な表への切り替え (BM-102a と BM-101a がそれぞれ約 1.2 ms 短くなる見込み。試作して測ってはいない) で、**v0.5 で入れる (PO の判断 2026-11-15)**。
2. **そのほかに本当の劣化は無い**: `perf-diff` (time) は警告なし。記録どうしで +10% を超えた行のうち、BM-103a の p99・BM-104-1m・BM-104p・BM-107 は交互の計測で差が無い (1 ms 未満の揺れ)。BM-103b-search は p50 +0.1 ms / p99 +0.5 ms の小さな差が残るが、ラウンド 2 はほぼ同じで、目標 (p50 2 / p99 8 ms) に対して小さいので揺れの範囲と見る。BM-205 (exe の大きさ) は 5,115,904 → 6,323,200 バイト (+23.6%)。v0.4 で足した機能 (行をまたぐ正規表現の行の窓・CP932 互換文字の同一視・区分 B の保持方式の記録・標準入力・書記素の単位の索引の表・高コントラストのテーマ・ユーザーの言語ファイル) の分と見る (`cargo bloat` での内訳は取っていない。NFR-205 は Should の記録)。
3. **BM-106 の v0.4 の判定 (AC-4、Should、p99 ≤ 50 ms)**: 3 種 × 5 操作は、一式の値で最大 15.81 ms、交互の計測の 3 回の rc.1 で最大 34.52 ms (japanese の `end`)。すべて速い状態の値。09 §5.2 は「判定は遅い側の値で行う」としているが、今回も遅い状態に入らなかった。遅い状態 (約 2.3 倍) の見込みでは japanese・emoji の `end` と `open` の p99 (約 25〜35 ms) が 50 ms を超えうる (100 ms (Must) は超えない見込み)。M25 の (5) の所見と同じ。

5. **BM-104v (FR-122 AC-2)**: UTF-8 は全読込が約 90〜110 ms (速い状態) なので、30 回のうち 29 回は全文の Frame で、p50 124 ms。Shift_JIS は全回が先行表示の先頭の Frame で、p50 205 ms (M25 の 206 ms と同じ)。どちらも 300 ms に対して約 95 ms 以上の余裕。

8. **計測の手順の注意**: `cargo build --release -p evoeditor` (BM-205) の後は、同じ `CARGO_TARGET_DIR` の `evoeditor.exe` が `bench-trace` なしに置き換わるので、`bm_pty` の実行ファイルを直に起動すると判定の区間 (BM-101a など) が出ない (端末込みの値だけになる)。交互の計測の rc.1 の最初の 1 回がそうなったので、`cargo bench --no-run -p evoeditor --features bench-trace --bench bm_pty` で組み直して測り直した (その回の値は捨てた)。`cargo xtask bench` の中は `bm_pty` の前に組み直すので、上の表には影響しない。
