# 性能の記録 — 開発機 (v0.5 の M31 の段 4: ワークスペースの走査の BM-125s)

v0.5 のリリースゲートの前の、マイルストーンの作業の記録 (docs/09 §5.3)。**基準機の値ではない** (参考値)。リリースゲートの判定は基準機で測り直した値で行う。

- コミット: `develop` の `af3e75f` に、M31 の段 4 (`feat/eve-core-workspace-scan`、PR #609) の変更を足した作業ツリー
- 環境: 開発機 (基準機ではない。Windows 11、性能の違う 2 種類のコアを持つ CPU、内蔵の NVMe SSD)。Linux は同じ機械の WSL2 (ext4)
- 確かめること (03 §12.7.9 の段 4 の完了の条件): 走査の間の `io` / `bg` のジョブの開始の遅れが、S-26 (`spikes/S-26/REPORT.md`) と同じ桁であること
- コマンド: `cargo bench -p eve-host --bench bm_125s -- --tree <木> --runs 5 --probe-secs 20 --json` を 2 ラウンド続けて測った。コアを固定した診断は `--diag`
- 木: `cargo xtask gen-corpus --workspace large --seed 42` (ファイル 156,841。照合の後に残る候補は NTFS で 91,428、ext4 で 95,597)
- 区間:
  - 走査: 温め 1 回の後の 5 回。ジョブの投入から `ScanDone` まで
  - 区切り 1 回: 同じ木を `WorkspaceWalk::step` で直に回した 1 区切りの時間
  - 開始の遅れ: 走査を繰り返す間に 20〜80 ms ごとに投入した見張りのジョブの、投入から最初の FS の呼出しまで

## 判定 (段 4 の完了の条件)

- 走査の間の `io` の開始の遅れは 1 ms 未満 (S-26: 0.07〜0.26 ms)、`bg` は最大 10.5 ms (S-26: 20.5〜24.5 ms)。どちらも S-26 と同じ桁で、条件を満たす。`bg` が S-26 より小さいのは、区切りに 8 ms と 4,096 項目の上限があるため。

## 所見

- 走査の時間は S-26 の試作の約 1.5 倍 (NTFS 0.56〜0.62 s 対 0.36〜0.77 s、ext4 0.30 s 対 0.17 s)。コアを固定した診断 (`--diag`) では、高性能のコアで「列挙だけ (全ディレクトリ)」375〜497 ms に対して走査 554〜558 ms、省電力のコアで 563〜614 ms 対 872〜937 ms。
- 照合の速さを直す前 (`**/node_modules` などの既定の除外が全項目に字句の模擬で当たっていた) は、高性能のコアで 825 ms (既定の除外なしで 600 ms)、最初の通しの計測で中央値 1,500 ms だった (記録には使っていない)。`Program::PathTail` などの修正の後の値が上の表。
- **OQ-103 の条件 (基準機で S-26 の (3) を測り直す) はここでは測っていない** (基準機と、比べる相手の `ignore::WalkParallel` の使い捨ての道具が要る)。開発機の値に、固定 2 本で譲る判断を変える材料は無い。BM-405 と合わせて、基準機の値で判断する。
