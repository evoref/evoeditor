# 性能の記録 — 開発機 (v0.5 の M31 の段 7: 横断検索の BM-103b-search-ws / BM-405)

v0.5 のリリースゲートの前の、マイルストーンの作業の記録 (docs/09 §5.3)。**基準機の値ではない** (参考値)。リリースゲートの判定 (BM-103b-search-ws の p50 2 ms / p99 8 ms。01 FR-405 AC-3、NFR-103) は、RC で基準機で測り直した値で行う。BM-405 は参考値で、合否を付けない。

- コミット: `feat/eve-core-workspace-search` の `b6bdc03` (PR #617。develop の `59a5719` を取り込み、レビューの修正 (読込のバッファを `min(1 MiB, 大きさ + 1)` にした・区切りを 8 ms に収めた) を含む)
- 環境: 開発機 (基準機ではない。Windows 11、性能の違う 2 種類のコアを持つ CPU、内蔵の NVMe SSD)。端末は ConPTY (`bm_pty`)
- コマンド: `cargo bench -p evoeditor --features bench-trace --bench bm_pty -- --only 103ws,405 --workspace-tree <木> --runs 1000`
- 木: `cargo xtask gen-corpus --workspace large --seed 42` (ファイル 156,841・ディレクトリ 10,112。除外の後に探すファイル 90,660)。内蔵の SSD の NTFS に置いた
- 手順: 木を `DIR` で開き、ファインダの走査を終えて閉じてから、`Ctrl+K F` で横断検索を開く
  - BM-103b-search-ws: 一致しない語 `zqxj` を入れ (検索の完了は待たない)、`k` と `BackSpace` を 30 ms ごとに交互に 1,100 回 (ウォームアップ 100 回を除く 1,000 回) 打つ。`k` の `input.to_flush`
  - BM-405-<名前>: 検索語の最後の 1 文字の前までを打ち、最後の 1 文字の打鍵の読取完了 → 最初の一致の行 (`-first`) / 完了の件数の欄 (`-done`) を描いた Frame の `write` (区間の記録 `search.first_match` の一覧の版)。それぞれ別のプロセスで 5 回ずつ
    - `literal` = `leaf` / `regex` = `pro[b]e|leaf` (正規表現) / `many` = `editor` (件数の上限に届く) / `sjis` = `\x{65E5}\x{672C}\w` (正規表現。木の Shift_JIS・EUC-JP・UTF-16 のファイルの「日本」)

## 所見

- 打鍵の判定区間 (BM-103b-search-ws) は、横断の走査が走り続ける間も p99 1.02 ms で、目標 (p50 2 ms / p99 8 ms) の内。記録は 1,000 件 (送った打鍵の数と同じ)。
- 10 万ファイルの木を最後まで探すのに約 17 秒 (約 5,400 ファイル/秒)。同じ日のレビューの修正の前の測定 (読込のバッファが毎回 1 MiB) は、`literal` 31.0 秒・`regex` 28.8 秒・`many` 11.2 秒・`sjis` 54.1 秒 (完了の p50) だった。バッファの確保をファイルの大きさに合わせたことで、`literal` / `regex` で約 46 % 減り、`sjis` で約 69 % 減った。
- 修正の後は `sjis` (正規表現の `\w`) も `literal` と同じ約 17 秒なので、照合ではなく、ファイルを 1 つずつ `bg` の 1 本のレーンで開いて読む費用 (OS のファイルを開く費用、ウイルス対策の検査を含む見込み。切り分けはしていない) が主になっている。レーンの構成 (OQ-103) は RC の基準機の値で判断する。
- 最初の一致までの時間は、一致が木の中のどこにあるかで決まる。`literal` / `regex` の最初の一致は名前の順で前にある `deep/` にあり約 16 ms、`many` / `sjis` の最初の一致は後ろにある `src/` にあり約 2.1 秒 (修正の前は 3.9〜6.1 秒)。
- 結果の JSON は保存していない (基準機の RC の計測で `--json` を付けて記録する)。
