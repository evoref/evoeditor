## 所見

- **FR-122 AC-2 は満たす**: p50 は UTF-8 168 ms、Shift_JIS 206 ms で、目標 300 ms に対して約 94 ms 以上の余裕がある。最大値も 211 ms。
- **Shift_JIS** は全読込が約 420 ms (`docs/perf/0.3.0/` の BM-104-100m-sjis p50 416 ms) なので、全回が先行表示の先頭の Frame。値はほぼ「先行表示を出す条件の 200 ms (03 §9.2.1 の `PARTIAL_AFTER`) + その後の最初のチャンクの区切り + 先頭の木の構築と Frame」で、揺れは小さい (6 組の p50 の幅 1 ms)。300 ms との差 (約 94 ms) は、200 ms の起点 (`open_read` の開始) までの経路と、先頭を送ってから描くまでに使える分。
- **UTF-8** は全読込が 200 ms の前後 (0.3.0 の BM-104-100m p50 180 ms) なので、多くの回 (79 %) は全文の Frame、読込が 200 ms を超えた回 (21 %) は先行表示の先頭の Frame (約 204〜208 ms) になる。そのため値は約 208 ms で頭打ちになり、p50 は全読込の時間の揺れ (組 1 (文) は 192.56 ms で先行表示 11 回) に従って動く。03 §9.2.1 の「UTF-8 の 100 MB では多くの場合に出さない」のとおり。
- UTF-8 の各組で、ウォームアップの後の最初の 2 回は約 110 ms で、3 回目以降 (約 160 ms〜) より速い (Shift_JIS では見えない)。100 MB の文書を閉じた後の開き直しの費用の違いと見るが、原因は調べていない (判定には影響しない)。

### 測った条件

- 4 つの組を 1 ラウンドに 1 回ずつ、3 ラウンド測った (13:21〜13:46 の約 25 分)。順は交互 (ラウンド 1 と 3 は「前 × v0.3.0 → 後 × v0.3.0 → 前 × この版 → 後 × この版」、ラウンド 2 はその逆順)。値は各ラウンドの p50 / p99 の中央値で比べた。
- 各組を起動する前に、全体の CPU の使用率を 1 秒ごとに 5 回見た: ほとんどが 0.4〜15 %。ラウンド 1 の「前 × この版」と「後 × この版」の直前だけ、別の作業の cargo のプロセスが 2 つあり、使用率は 10〜27 % だった。その 2 つのラウンド 1 の値は、ほかのラウンドと幅の中で揃っている (例: 後 × この版の ascii の `end` の p99 は 41.18 / 40.24 / 40.56 ms) ので、捨てずに中央値に入れた。
- 電源に接続。Defender のリアルタイム保護は無効 (環境の登録どおり)。ヘッドレス (`Harness`、120 × 40) で、ファイルは `MemFs` の上 (ディスクの I/O を含まない)。実行ファイルは外付けの SSD の上 (区間にはプロセスの起動を含まない)。
- Rust 1.99.0、`bench` プロファイル (release + debuginfo)。
- 開発 PC (基準機 `ENV-W1`) は、計測の前後に別の作業の cargo のビルド・試験が走る。上の確認の外の時間 (ラウンドの途中) に負荷が入った可能性は残る。

### 所見

- **v0.2 の判定 (p99 ≤ 100 ms、Must) は、組み替えた計測でも割らない**: この版の 5 つの操作の p99 は最大でも ascii の `end` の 40.56 ms。3 種のコーパスの 5 つの操作はすべて 50 ms (v0.4 の Should) の内側にもある (判定は (5) で書記素の単位に切り替えた後に行う)。
- **組み替えで見えるようになったもの**: 組み替えの前の `end` は、索引ができた後の `Home` → `End` (行末の位置は記録点からの差分で引く) なので、v0.3.0 でもこの版でも 0.2〜0.4 ms しか測っていなかった。この版は索引を開いた直後に作らないので、行末までの 1 回の走査が 1 回目の `End` に移る。前のプログラムでは、その 1 回が「後ろの 2 回目以降」に紛れて最大値 (ascii 14.6〜15.3 ms、japanese 16.5〜28.5 ms、emoji 17.3〜32.3 ms) にだけ出ていた。組み替えた後のプログラムはそれを 100 回分の分布として測る。
- **v0.3.0 → この版 (組み替えた同じプログラムで)**: 開く (`open`) は行末までの索引を作らなくなった分だけ速い (p99 で ascii 48.65 → 13.11 ms、japanese 61.85 → 32.01 ms、emoji 63.66 → 26.69 ms)。その分が `End` に移り、`end` は 0.2〜0.5 ms → 27〜41 ms になった (行末までの走査の費用。`open` と `end` の p50 の和は、どちらの版も 31〜42 ms でほぼ同じ)。中央挿入 (`insert_mid`) は、行の全体の作り直し (v0.3.0 の p99 29〜46 ms) が、変更の位置の手前の記録点から画面の分までの作り直しになり、p99 で 0.6〜1.3 ms になった。参考の `end_after_insert` は、v0.3.0 では挿入の時点で行の全体を作り直すので `End` は 0.4〜0.5 ms、この版は変更の位置 (行の中央) から行末までを作るので 13.7〜20.9 ms (`end` のおよそ半分)。
- ascii の `end` の p99 (約 40 ms) は p50 (約 14〜29 ms) より大きく、japanese・emoji より遅い。ASCII は 1 バイト = 1 char で char の数が 10 MB 分あり (japanese・emoji の約 3 倍)、char ごとの走査 (ASCII も 1 char ずつ `CharWidth::of` を通る) の費用が char の数に比例するため。印字できる ASCII の連続をまとめて数える高速経路 (03 §14.4 の「走査」の (a)) は (5) で入れる。
- v0.3.0 の値は `docs/perf/0.3.0/BM-106.json` (例: ascii の `open` の p99 48.94 ms、`insert_mid` の p50 24.26 ms) と同じ程度で、前のプログラム × v0.3.0 の `open` の p99 (54.63〜71.23 ms) はそれより揺れが大きい。同じ時間帯に交互に測った組どうしで比べる。

### 測った条件

- BM-106: 2 つの木を 1 ラウンドに 1 回ずつ、3 ラウンド (21:35〜22:50。ラウンド 1 と 3 は develop → この版、ラウンド 2 は逆)。各回の前の CPU の使用率は、ほとんど 0〜10 %。ラウンド 3 の develop の直前だけ 8〜27 % だった (その回の値は、ほかのラウンドの幅の中に入っている)。cargo・rustc のプロセスは無かった。
- 最悪の入力: 同じように 3 ラウンド (22:54〜23:00)。各回の前の CPU の使用率は 0〜8 %。BM-106 の後に、32 バイトを超える 1 書記素の幅を最後の 1 つだけ覚える直しを入れて測り直した (BM-106 の 9 種のコーパスには 32 バイトを超える書記素が無いので、BM-106 の値には効かない)。
- 電源に接続。Defender のリアルタイム保護は無効 (環境の登録どおり)。ヘッドレス (`Harness`、120 × 40)、ファイルは `MemFs` の上。実行ファイルは内蔵の SSD の上。
- `bench` プロファイル (release + debuginfo)。最悪の入力のプログラムは release (fat LTO)。

### 所見

- **v0.2 の判定 (p99 ≤ 100 ms、Must) を割らない** ので、この PR を入れる条件を満たす。**v0.4 の判定 (p99 ≤ 50 ms、Should) も、判定の 3 種のコーパスの 5 つの操作のすべてで内側** (最大は emoji の `end` の p99 40.35 ms)。ただし速い状態の値で、遅い状態 (約 2.3 倍) では emoji と japanese の `end` は 50 ms を超えうる (100 ms は超えない見込み)。
- **参考のケースと最悪の入力の実在の文字は、どれも `End` と `end_after_insert` が 100 ms の内側** (BM-106 の参考のケースの p99 の最大は flags の `end` 75.52 ms、ivs の `end` 75.59 ms)。遅い状態では、この 2 つは 100 ms を超えうる。
- **レビューの前 (この PR の最初の版) からの変化**: 書記素の分割を `unicode-segmentation` の呼び出し (1 書記素あたり 30〜100 ns) から表引きの経路 (約 10 ns) に替え、複数の char の書記素の幅を表示を組み立てずに求めて覚えたことで、レビューの計測で 116〜396 ms だった実在の文字の行 (韓国語・タイ語・デーヴァナーガリー・ZWJ の家族・国旗・IVS・FE0F 付きの絵文字・字母 LVT) が 23〜43 ms になった。ハングルの音節を表から外したので、韓国語の文は書記素の分割に回らない。
- **病的な入力**: 1 書記素がとても長い行は、分割に渡す範囲を上限 (4 KiB と 1 文字) までにし、長い書記素の幅を最後の 1 つだけ覚えたことで、レビューの計測の 175〜611 ms が 14〜28 ms になった。**Prepend と ASCII の組の繰り返し** (`؀a`) だけは 77 ms (最大 83 ms) 残る。原因は、U+0600 (Prepend) が後ろの char と必ず結合するので、3 バイトごとに 2 char の書記素になり、どれも表引きの分割と幅の覚えを通るため (10 MB で約 350 万個、1 個あたり約 22 ns)。100 ms の内側だが、03 §14.4 の既知の制約に書いた。
- **japanese・emoji の `end`**: develop より、最悪の入力の計測 (同じ状態で交互) で japanese +8 %、emoji +21 % (BM-106 の p99 では japanese 28.03 → 33.30 ms、emoji 21.51 → 40.35 ms)。表に無い char の連続でも、char ごとに表を 1 回引く分。ascii の `end` は、まとめて数える経路で 38.25 → 5.42 ms。
- `insert_mid` は、記録点の間隔を 64 KiB から 4 KiB にした分だけ作り直しが短く、どのケースも p99 0.4 ms 以下。

## BM-106w (M25 の 6: 長大行の折り返しの判定)

- 記録: `BM-106w-spike.json` (試作の BM-106w)、`BM-106-wrap-spike.json` (試作の版の折り返しなしの BM-106)、`BM-106-develop-1568986.json` (比べる develop の BM-106)

### 折り返しなしの BM-106 (03 §14.4 の 4 の (b))

develop と交互に、計 9 ラウンド (run1 3・run2 2・run3 は japanese だけ 4)。同じ組の中で比べて劣化は見られない (例: japanese の `end` の p50 は run1 で develop 11.74〜11.80 / 試作 11.77〜11.97 ms、run3 で 18.06〜18.12 / 17.96〜18.19 ms。run3 は run1 と別の状態)。試作の run2 の 1 ラウンド目は途中で一時的に遅くなった (japanese の `end` の p50 22.89 ms) ので比べない。p99 には両方に 1 回ずつ 32 ms 前後の外れ値がある。折り返しなしの経路の変更は分岐 1 つと覚えの引き方だけ。

### 判定 (03 §14.4 の 4)

- (a) 各操作 p99 ≤ 100 ms: 3 種は速い状態で最大 39.4 ms。遅い状態の見込みでは emoji の `end_line` が 91 ms で余裕が 1 割に満たず、参考の korean は 146 ms で超える。非 ASCII の表示の単位 1 つあたり約 5 ns の上乗せで、折り返しなしの走査の 2.5〜2.7 倍。
- (b) 折り返しなしの BM-106 が劣化しない: 満たす。
- (c) 製品の品質に仕上げる工数 2 週以内: **満たさない**。残る作業の見立ては約 11.5 日 (10.5〜12.5 日): 索引の設計の確定 1.5、速さを詰める 2.5 (成否は読めない)、遅延の残り 1.5、試験 2.5、境界の場合 1、仕様と文言 1、レビューと記録 1.5。M25 の中の作業なので M26・M27 がそのぶん遅れる。
- **結論: v0.5 以降に送る** (08 §7、01 §4.6)。試作のブランチは v0.5 で入れるときの土台として残す。
